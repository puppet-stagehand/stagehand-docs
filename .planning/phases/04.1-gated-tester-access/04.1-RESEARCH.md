## Summary

This phase adds a path-scoped shared-password gate to the CloudFront edge and ports one large
piece of content behind it. The Terraform side is well-supported: the AWS provider pinned in this
repo (`~> 6.0`, resolved locally to 6.61.0) ships `aws_cloudfront_key_value_store` for the
container and `aws_cloudfrontkeyvaluestore_key` for individual key/value pairs (note the
collapsed-name resource — this is **not** `aws_cloudfront_key_value_store_key` as the phase
description's own investigation prompt guessed), plus a `key_value_store_associations` set
attribute directly on `aws_cloudfront_function`. All three were confirmed against the actual
locally-cached provider schema, not training memory.

The single biggest non-obvious finding: **all three real, currently-deployed environments already
have a whole-site HTTP Basic Auth lockdown active** (`enable_basic_auth = true` in
`infra/environments/{testpilots,beta,stable}/main.tf`, wired through the very same
`aws_cloudfront_function.redirect` this phase must extend). That mechanism bakes the expected
`Authorization` header directly into the function's *source code* via Terraform string
substitution — changing it forces a function republish, which is exactly what AUTH-03 says the new
mechanism must NOT require. The new gate cannot simply extend that pattern; it must add a
KVS-backed, path-scoped check, and the plan needs to explicitly decide whether/when the blanket
`enable_basic_auth` lockdown is retired now that a real, narrower mechanism exists (leaving both
active would 401 every page, including deliberately-ungated ones like `/downloads/` in Phase
04.2).

The second major finding: neither `npm run check:links` nor the Playwright `production` project
ever exercises the CloudFront function at all — both serve the local `dist/` build through a bare
`http.createServer` with zero auth logic. AUTH-04's requirement is satisfiable by recording this
fact, not by building parity infrastructure. GATE-06 is best satisfied the same way GATE-05
already is — a pure function-level unit test using the existing `vm.runInContext` harness pattern
in `infra/modules/static-site/tests/`.

The Tester's Guide source (`puppet-console/docs/TESTER-GUIDE.md`, 1375 lines) has no images or
relative links, so it is *mechanically* portable without broken references. But it is an internal
engineering QA changelog (phase-numbered checklists, Go/TypeScript test commands runnable only
from a source checkout, references to `puppet-console`'s own `.planning/HUMAN-TESTS-DEFERRED.md`)
— whether the locked D-01 decision means porting it verbatim or trimming it to genuinely
external-tester-facing content is not resolved by CONTEXT.md and should be confirmed with a human
before the plan commits to one approach.

**Primary recommendation:** Extend the existing `redirect.js`/`aws_cloudfront_function.redirect`
with a path-scoped, KVS-backed Basic-Auth check (password only, no username enforcement); manage
the KVS container in Terraform but write the actual secret value out-of-band via
`aws cloudfront-keyvaluestore put-key` documented in a new `docs/operations/tester-access.md`
runbook; declare the gated-path list in one small JSON file read by both Terraform and whatever
test/AUTH-04 documentation needs it; prove the gate logic with a pure unit test alongside
`redirect.test.mjs`; and resolve the existing whole-site `enable_basic_auth` lockdown as part of
this phase's scope rather than leaving it stacked underneath the new mechanism.

### Pattern 1: Path-scoped KVS-backed Basic Auth, layered into the existing function

**What:** Add a guard clause to `redirect.js`'s `handler` that runs *before* the existing
apex-redirect/clean-path logic, matching only requests whose `uri` starts with a declared gated
prefix, and checking the request's `Authorization` header's password component against a KVS
lookup rather than a compiled-in string.

**When to use:** Any time a shared secret needs to gate a subset of paths on a CloudFront
distribution without a second function (which CloudFront does not allow) and without requiring a
function republish to rotate the secret.

**Example (illustrative shape, not the literal final file — the exact `cf.kvs()` call signature is
an open question, see below):**
```javascript
// Source: infra/modules/static-site/functions/redirect.js (existing structure)
// [VERIFIED: infra/modules/static-site/functions/redirect.js:1-68 — existing unauthorized()/handler shape]
import cf from 'cloudfront'; // [ASSUMED — exact import form not verified against AWS docs this session]

var GATED_PATH_PREFIXES = __GATED_PATH_PREFIXES__; // Terraform-templated JSON array literal, from gated-paths.json

function isGatedPath(uri) {
  for (var i = 0; i < GATED_PATH_PREFIXES.length; i += 1) {
    if (uri.indexOf(GATED_PATH_PREFIXES[i]) === 0) return true;
  }
  return false;
}

function extractPassword(authHeaderValue) {
  // "Basic <base64(username:password)>" — username is ignored per AUTH-01 ("no username")
  var decoded = /* base64 decode via atob-equivalent available in the CF Functions runtime */;
  var colonIndex = decoded.indexOf(':');
  return colonIndex === -1 ? decoded : decoded.substring(colonIndex + 1);
}

async function handler(event) {
  var request = event.request;
  var uri = request.uri;

  if (isGatedPath(uri)) {
    var authHeader = request.headers.authorization;
    var expected = await cf.kvs().get('gate_password'); // [ASSUMED syntax — verify with `aws cloudfront test-function` before trusting]
    if (!authHeader || extractPassword(authHeader.value) !== expected) {
      return unauthorized(); // reuses the existing unauthorized() helper verbatim
    }
  }

  // ... existing apex-redirect / clean-path / index.html rewrite logic, unchanged below this point
}
```

### Pattern 3: CSP-safe client-side hostname detection

**What:** A plain (non-`is:inline`) `<script>` block in an `.astro` component, which Astro bundles
into an external, same-origin `/assets/*.js` file at build time — satisfying this site's strict
`script-src 'self'` CSP with no inline-script exception needed.

**Existing precedent already proven to work under this exact CSP:**
```javascript

<script>
  const matrix = document.querySelector<HTMLElement>('[data-compatibility-matrix]');
  if (matrix) {
    const form = matrix.querySelector<HTMLFormElement>('[data-compatibility-filters]');
    // ...
  }
</script>
```

**Recommended new utility (shared with Phase 04.2 per CONTEXT.md's discretion note):**
```typescript
// src/lib/site-channel.ts — pure, unit-testable without a DOM
export type SiteChannel = 'testpilots' | 'beta' | 'stable' | 'unknown';

export function resolveSiteChannel(hostname: string): SiteChannel {
  // [VERIFIED: exact hostnames from infra/environments/*/main.tf]
  if (hostname === 'testpilots.puppet-stagehand.com') return 'testpilots';
  if (hostname === 'beta.puppet-stagehand.com') return 'beta';
  if (hostname === 'www.puppet-stagehand.com' || hostname === 'puppet-stagehand.com') return 'stable';
  return 'unknown';
}
```
```astro
<!-- in DocsLayout.astro, only when entry.data.visibleOn is set -->
<script>
  import { resolveSiteChannel } from '../lib/site-channel';
  const guide = document.querySelector('[data-tester-guide]');
  const fallback = document.querySelector('[data-tester-guide-unavailable]');
  const channel = resolveSiteChannel(window.location.hostname);
  const allowed = ['testpilots', 'beta'].includes(channel);
  guide?.toggleAttribute('hidden', !allowed);
  fallback?.toggleAttribute('hidden', allowed);
</script>
```
Note: because the identical static bytes ship to `stable`, the full guide markup is still present
in the page source there (view-source would reveal it) — the client script only toggles visual
`hidden`. This is a deliberate, low-risk tradeoff already implied by D-02's "client-side hostname
detection" choice and by D-03 ("a separate, additional runtime concern layered on top of the
access gate, not a replacement for it") — the path is still password-gated identically on all
three environments, so a tester who can see it on `stable` already had legitimate access to the
same content on `testpilots`/`beta`. Flag this explicitly in the plan so it isn't mistaken for a
security gap needing a build-time fix.

### Anti-Patterns to Avoid
- **Building a second CloudFront Function for the gate:** not supported — only one function may be
  associated per event type per cache behavior. Extend `redirect.js`.
- **Simulating the edge gate inside `scripts/serve-static-build.ts` or Playwright's local server:**
  over-engineering relative to what AUTH-04 actually requires (an explicit recorded exclusion, not
  parity infrastructure) and explicitly warned against by the phase's own scope note ("should NOT
  build a general-purpose per-environment content framework").
- **Managing the KVS key's plaintext value in Terraform:** works, but weakens the rotation story
  AUTH-03 wants (a runbook-driven CLI write, no apply needed) and re-introduces the secret into
  Terraform state for no benefit.
- **A per-environment build to hide the Tester's Guide on stable:** directly forbidden by
  PROJECT.md's immutable-promotion constraint; D-02 already resolved this via client-side
  detection — don't re-litigate it in the plan.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Mutable edge-readable secret storage | A DynamoDB table + Lambda@Edge lookup, or a hand-rolled S3-object-as-config fetch from within the Function | `aws_cloudfront_key_value_store` + `cf.kvs()` | Purpose-built AWS primitive for exactly this; already compatible with the runtime this repo uses (`cloudfront-js-2.0`) |
| Testing edge JS logic | A real deployed CloudFront distribution + live HTTP requests in CI | `node:vm` + the existing `redirect.test.mjs` harness pattern | Already proven in this repo for the apex-redirect/basic-auth logic; instant, no AWS credentials needed in CI |
| Local dev-server auth parity | Basic Auth middleware bolted onto `scripts/serve-static-build.ts` | An explicit, documented exclusion rule (AUTH-04) plus the function-level unit test (GATE-06) | The local server's job is serving static files for link-checking and UI e2e tests, not proving the edge gate — that's what the CloudFront-function unit test is for |
| Environment/channel resolution | A server-rendered per-environment build, or a cookie/header-based server check | `window.location.hostname` read in a small client script | Static-only site, no SSR; immutable promotion forbids per-environment builds by design |

**Key insight:** everything this phase needs already has a first-class AWS or in-repo precedent —
KVS for mutable edge config, the existing function-test harness for edge-logic verification, and
plain client `<script>` tags (already proven under this CSP) for the environment check. The risk
in this phase is not missing tooling, it's stacking a new mechanism on top of an old one
(`enable_basic_auth`) without reconciling them, and porting a very large, internally-scoped
document without confirming its audience fit.

`infra/environments/stable/main.tf:51`], baked in via the same `aws_cloudfront_function.redirect`
this phase must extend. If the plan adds the new path-scoped gate without addressing this, either
(a) the whole site stays 401'd for everyone including on ungated paths like the future
`/downloads/` page, or (b) two independent auth mechanisms coexist confusingly.
**Why it happens:** The lockdown was added recently (commit `44b56c9`, "temporary HTTP Basic Auth
lockdown to all environments") as a stopgap before real content/tester access shipped — it predates
this phase's design.
**How to avoid:** The plan should explicitly decide (and probably execute) turning
`enable_basic_auth` off as part of this phase, now that a real, narrower mechanism exists to
protect the specific content that needed protecting.
**Warning signs:** `check-live-deployment.ts`-style live checks against real routes start
returning 401 instead of 200 for pages that should be public.

### Pitfall 2: Only one function per event type per cache behavior
**What goes wrong:** Attempting to declare a second `aws_cloudfront_function` for the gate and
associate it alongside `redirect` on the same `viewer-request` event silently isn't representable
in Terraform's `function_association` block (one per event type) and isn't supported by CloudFront
itself.
**Why it happens:** Natural instinct to keep concerns separate by writing a new function.
**How to avoid:** Add the gate logic as an early guard clause inside the existing `redirect.js`
`handler`, before its current logic.
**Warning signs:** `tofu plan` shows only the last-declared function association taking effect, or
the AWS console shows only one function attached per behavior.

### Pitfall 3: `check:links`/Playwright never see the edge gate at all
**What goes wrong:** Assuming AUTH-04 requires teaching the local dev/test server about the
password (or explicitly excluding the gated URL from a crawl config) when in fact
[VERIFIED: `scripts/check-links.ts:1-33`, `playwright.config.ts:1-45`, `scripts/serve-static-build.ts:1-52`]
neither tool ever passes through CloudFront — both serve the local `dist/` directly with zero auth
logic, so they'll crawl the gated page successfully with no credential regardless.
**Why it happens:** AUTH-04's wording ("carry the credential or exclude the gated paths...so
neither tool silently reports success because it stopped crawling") reads as if these tools
exercise the live edge; they don't, they exercise the local static build.
**How to avoid:** Satisfy AUTH-04 by recording this fact explicitly (a comment near the gated-path
declaration, or a line in the new runbook) rather than building parity infrastructure that doesn't
match what these tools actually test.
**Warning signs:** A plan task that tries to add `Authorization` headers to `linkinator`'s config or
Playwright's `use.extraHTTPHeaders` — unnecessary, since there's no edge in the loop to authenticate
against locally.

### Pitfall 4: `docs-collection.test.ts` has a closed enumeration
**What goes wrong:** [VERIFIED: `tests/unit/docs-collection.test.ts:33-40` — `expect(entries.map(({ slug }) => slug).sort()).toEqual(['first-run', 'getting-started', 'security'])`]
this test asserts the *exact* set of doc slugs. Adding `testers-guide.md` without updating this
array fails `npm run verify` immediately on the unit-test stage, before the build even runs.
**Why it happens:** The test was written when three entries were the complete, closed set; it
wasn't written to auto-discover new ones.
**How to avoid:** Update the `.toEqual([...])` array in the same change that adds the new content
file.
**Warning signs:** `vitest` failure in `docs collection source` describe block immediately after
adding the markdown file.

### Pitfall 5: Hardcoded route/invalidation lists need the new page added
**What goes wrong:** [VERIFIED: `scripts/check-built-routes.ts:4-15`] the required-outputs list is
a fixed array, and [VERIFIED: `scripts/check-invalidation-coverage.ts:1-53`, `scripts/deploy-site.sh:46-49`]
the invalidation-coverage check auto-discovers every built `.html` route and fails if it's missing
from `deploy-site.sh`'s `--paths` list (this one is self-enforcing — GATE-03 already exists and
will catch a missed addition — but it still needs the edit made).
**How to avoid:** Add `docs/testers-guide/index.html` to both `check-built-routes.ts`'s array and
`deploy-site.sh`'s invalidation list in the same change that adds the content.

### Pitfall 6: CSP forbids inline scripts — use bundled `<script>`, not `is:inline`
**What goes wrong:** [VERIFIED: `infra/modules/static-site/cloudfront.tf:90` —
`script-src 'self'`, no `'unsafe-inline'`, no nonce/hash] an `is:inline` Astro script tag, or a
literal `onclick=` attribute, would be silently blocked by the browser at runtime with no build
error.
**How to avoid:** Use a plain `<script>` tag (no `is:inline` directive) as
`CompatibilityMatrix.astro` already does successfully — Astro bundles it to an external, same-origin
file automatically.

### Pitfall 7: `vm.runInContext` can't literally run `import cf from 'cloudfront'`
**What goes wrong:** The existing `redirect.test.mjs` harness runs the function source as a plain
script inside `vm.createContext({})` via `vm.runInContext` — this does not support ES `import`
syntax (it's not evaluated as an ES module).
**How to avoid:** Following the same placeholder-substitution technique the harness already uses
for `__ENABLE_BASIC_AUTH__` etc., strip or replace the `import cf from 'cloudfront';` line before
evaluating, and inject a mock `cf` object into the `vm.createContext({...})` call
(`{ cf: { kvs: () => ({ get: async (key) => mockValues[key] }) } }`) so `await cf.kvs().get(...)`
resolves against test fixtures.
**How to avoid also (async):** since the handler will be `async function handler(event)`, the test
must `await context.handler(event)` (or handle the returned Promise) — `redirect.test.mjs`'s
existing tests call `context.handler(...)` synchronously, which will need updating for any test
that exercises the new async gate branch.

### Pitfall 8: Unverified CloudFront Functions KVS runtime API
**What goes wrong:** This session had no internet access (`WebSearch`/`WebFetch`/the project's
Brave-backed `gsd_run query websearch` all failed) to confirm the exact `cf.kvs()` call signature,
whether the handler must be declared `async`, and which event types support KVS reads. Getting this
wrong means the function fails at publish time or at request time in a way local unit tests (which
mock `cf`) won't catch.
**How to avoid:** Before trusting the mocked unit tests, run one real
`aws cloudfront test-function --stage DEVELOPMENT` against an actual (unpublished) function version
with a real KVS association, to confirm the exact API shape — see Open Questions.

### Pitfall 9: TESTER-GUIDE.md is an internal engineering changelog, not tester-facing prose
**What goes wrong:** The 1375-line source [Read in full this session] is structured as a running,
dated changelog of `puppet-console`'s own internal QA history — phase-numbered checklists (Phase
22, 23, 25, 26.4, 27, 28...), Go/TypeScript test invocation commands runnable only from a
`puppet-console` source checkout (`PSH_TEST_DATABASE_URL=<dsn> go test ...`), and dozens of
references to `puppet-console`-internal files (`.planning/HUMAN-TESTS-DEFERRED.md`,
`docs/design/core-v1-capabilities.md`, `docs/qa/*.md`, `docs/adr/0008-console-sbom.md`) that don't
exist in `stagehand-docs` and won't resolve for a reader here. None of these are markdown
hyperlinks (0 relative links found), so nothing will *break the build* — but a verbatim port ships
content whose primary audience appears to be `puppet-console`'s own contributors, not an external
tester of a deployed instance armed only with a shared password.
**How to avoid:** Confirm with a human (ideally via `/gsd-discuss-phase 04.1`) whether D-01 means a
verbatim port or a trimmed one before the plan commits engineering effort to either. See Open
Questions.

### Pitfall 10: Adding a new content-collection field requires a schema change
**What goes wrong:** [VERIFIED: `src/content.config.ts:1-15` — `schema: z.object({ title, description, order, updated })`]
zod's `z.object()` silently **strips** unrecognized keys by default (it does not throw on extras
unless `.strict()` is used) — so adding `visibleOn: ['testpilots', 'beta']` to the new markdown
file's frontmatter without also adding a matching field to this schema means the field is silently
dropped at parse time, and `DocsLayout.astro` would see `entry.data.visibleOn === undefined`.
**How to avoid:** Add the new optional field to the zod schema in the same change.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-------------------|
| V2 Authentication | yes | Shared-password HTTP Basic Auth at the edge (CloudFront Function), password-only comparison against a KVS-stored value; no username/identity concept — this is intentionally a shared-secret gate, not per-user auth (AUTH-01 explicit: "no username") |
| V3 Session Management | no | Stateless — every request is checked independently against the `Authorization` header; no session/cookie is issued or required |
| V4 Access Control | yes | Path-based: only paths matching the AUTH-05 declared list are gated; everything else passes through unaffected — the control is "is this URI in the gated set," not role-based |
| V5 Input Validation | yes | The `Authorization` header must be parsed defensively (missing header, malformed base64, missing colon) — see the `extractPassword` sketch in Code Examples, which must not throw on malformed input (an uncaught exception in a CloudFront Function is a hard failure for the whole request) |
| V6 Cryptography | partial | Base64 is *encoding*, not encryption — the password crosses the wire in a trivially reversible form, same as the existing whole-site Basic Auth already accepts (precedent: `basic_auth_password` is already handled this way in this repo). HTTPS (already enforced site-wide via `viewer_protocol_policy = "redirect-to-https"` [VERIFIED: cloudfront.tf:171,191,211]) is what actually protects the password in transit, not the Basic Auth scheme itself |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Password committed to the public repo (plaintext, hash, or "temporary" placeholder that's actually live) | Information Disclosure | AUTH-02's whole point — value lives only in KVS + the runbook's rotation procedure, never in a tracked file; `git grep` sweep as an explicit verification step (this repo already has precedent for this exact sweep, see `PUB-07`'s verification note in REQUIREMENTS.md) |
| Offline brute-force of a leaked hash | Information Disclosure / Spoofing | N/A here — no hash is ever published (unlike a bcrypt-hash-in-repo approach that AUTH-02 explicitly rejects); the only exposure surface is the KVS value itself, which requires AWS API access to read |
| Online brute-force of the password directly against the edge | Spoofing / Denial of Service | **Accepted risk, not mitigated by this phase** — CloudFront Functions have no built-in rate limiting; AWS WAF rate-based rules are explicitly deferred to v2 (OPS-03 in REQUIREMENTS.md v2 backlog). The plan should record this as an accepted risk in the runbook, consistent with this repo's existing pattern of explicitly naming accepted risks (e.g. PUB-07's account-ID exception) rather than silently ignoring it |
| Gated-path declaration drifting from what's actually enforced | Tampering (of trust, not of data) | AUTH-05's single-source-of-truth file, read by both the compiled function and whatever verification tooling checks it — the build-time contract this repo already leans on heavily (CONT-05, GATE-03) |
| Credential appearing in CloudFront/S3 access logs | Information Disclosure | Currently low residual risk — CloudFront/content-bucket access logging is itself deferred to v2 (OPS-02); if logging is ever enabled, the runbook should note that `Authorization` headers must be excluded/redacted from any log field configuration |
