## Summary

This is a re-review of gap-closure plan 04.1-05, which fixed CR-01 from the prior
04.1-REVIEW.md (Tester's Guide visibility toggle failing open instead of closed). This report
supersedes the prior 04.1-REVIEW.md in full.

**CR-01 fix verified correct and complete.** I traced the logic by hand and then empirically
verified it:
- Built the site (`npm run build`) and inspected `dist/docs/testers-guide/index.html` directly:
  the `.docs-content` div now server-renders with a literal `hidden` attribute whenever
  `entry.data.visibleOn` is set, and the `data-tester-guide-unavailable` fallback paragraph no
  longer carries a `hidden` attribute at all — the safe, fail-closed default is what ships in the
  static HTML, not something that depends on client JS running.
- Ran the three tests in `tests/e2e/tester-guide-visibility.spec.ts` against the built site
  (`playwright test tests/e2e/tester-guide-visibility.spec.ts --project=production`): all 3
  passed (Test A: no-JS default is fallback-visible/guide-hidden; Test B: beta hostname reveals
  the guide; Test C: stable hostname keeps it hidden).
- Confirmed via `grep` across all built `/docs/*/index.html` pages that the gating markup and the
  `TesterGuideVisibility` script are emitted only on `docs/testers-guide/index.html` — non-gated
  docs pages are untouched by this change, matching the commit's stated scope.
- Confirmed no CSS in `src/styles/components/_docs.scss` overrides the `[hidden]` UA default
  (`display: none`) for `.docs-content`, so the attribute-based hide/show actually has effect.

The inverted guard in `TesterGuideVisibility.astro` (`if (allowed) { unhide guide; hide fallback }`
with no `else`) is correct: because the fail-closed state is already what the server renders, the
script only ever needs to *promote* an allowed visitor out of the safe default, never demote a
disallowed one into it. This closes every failure mode named in the code comment (JS disabled,
blocked by extension/policy, slow/incomplete hydration, or a thrown exception before the reveal
line runs) — verified concretely by Test A with `javaScriptEnabled: false`.

No new correctness or security bugs were introduced by this specific change. The one finding
below (WR-01) is a **pre-existing** design gap in `TesterGuideVisibility.astro` (present since
its original introduction in `84be364`, untouched by the CR-01 fix) that I'm flagging because it's
in the file scope of this re-review and it's a real latent trap, not because it was introduced
here.

## Warnings

### WR-01: Client script ignores the actual contents of `entry.data.visibleOn`, hardcodes the allowed channel set instead

**File:** `src/components/TesterGuideVisibility.astro:18`
**File:** `src/layouts/DocsLayout.astro:61-62,67,98`

**Issue:** The content schema (`src/content.config.ts:12`) defines `visibleOn` as
`z.array(z.enum(['testpilots', 'beta', 'stable'])).optional()`, implying each gated doc can
declare *which specific channels* it's visible on. In practice, `DocsLayout.astro` only ever uses
`entry.data.visibleOn` as a boolean gate (`entry.data.visibleOn ? true : undefined`,
`entry.data.visibleOn && (...)`) — the array's actual element values are never read, and are never
passed down to `TesterGuideVisibility.astro` (no prop, no `data-*` attribute carrying the list).
The client script instead hardcodes its own allow-list:

```js
const allowed = channel === 'testpilots' || channel === 'beta';
```

Today this is harmless because the one gated document (`src/content/docs/testers-guide.md:6`) sets
`visibleOn: ['testpilots', 'beta']`, which happens to match the hardcoded pair exactly. But the
schema actively invites a future author to write, e.g., `visibleOn: ['testpilots']` (testpilots-only)
or `visibleOn: []` (hide from every channel) expecting the field to control per-channel exposure —
and neither would have any effect. A testpilots-only doc would still be revealed on beta; an
empty-array doc would still be revealed on both, because the script never consults the value, only
whichever two channels are wired into it. This is a silent contract violation between the schema
and the runtime behavior: the data model promises granularity the implementation doesn't deliver.

**Fix:** Thread the actual channel list from the entry into the client script, e.g.:

```astro
<!-- DocsLayout.astro -->
<div
  class="docs-content"
  data-tester-guide={entry.data.visibleOn ? true : undefined}
  data-tester-guide-channels={entry.data.visibleOn ? entry.data.visibleOn.join(',') : undefined}
  hidden={entry.data.visibleOn ? true : undefined}
>
```

```js
// TesterGuideVisibility.astro
const guide = document.querySelector<HTMLElement>('[data-tester-guide]');
const allowedChannels = (guide?.dataset.testerGuideChannels ?? '').split(',');
const channel = resolveSiteChannel(window.location.hostname);
const allowed = allowedChannels.includes(channel);
```

This makes the schema's per-document channel list authoritative instead of decorative, and removes
the silent drift risk the next time a second gated page is added (the docs comment in
`TesterGuideVisibility.astro` even calls out Phase 04.2's downloads page as a planned reuse site
for `resolveSiteChannel` — this is exactly where a mismatched hardcoded allow-list would first bite).

## Info

### IN-01: `entry.data.visibleOn` truthiness is re-evaluated four separate times in DocsLayout.astro

**File:** `src/layouts/DocsLayout.astro:61,62,67,98`
**Issue:** `entry.data.visibleOn ? true : undefined` / `entry.data.visibleOn && (...)` is repeated
four times across the template (lines 61, 62, 67, 98) instead of being computed once. Functionally
consistent today, but it's four places that must be kept in sync by hand on any future edit (e.g.,
if the gating condition ever needs to change from "is set" to "is set and non-empty").
**Fix:** Hoist to a single frontmatter constant and reuse it:
```ts
const isGated = Boolean(entry.data.visibleOn?.length);
```
then use `isGated` at all four call sites.

### IN-02: Tests B and C bypass the Playwright project config (no trace capture on failure)

**File:** `tests/e2e/tester-guide-visibility.spec.ts:40-46`
**Issue:** `gotoAsHostname()` calls `chromium.launch()` directly rather than using the
fixture-provided `page`/`context`, which is a documented, verified necessity (the comment at
lines 26-38 explains `Location.hostname` can't be redefined via `page.addInitScript`). A side
effect is that these two tests don't inherit `playwright.config.ts`'s `use.trace:
'retain-on-failure'`, `projects[0].use` device settings, or any other project-level configuration
— if Test B or C ever fails in CI, there will be no trace artifact to debug it with, unlike Test A.
**Fix:** Not blocking given the documented Chromium limitation, but consider wrapping the manually
launched page in a minimal manual trace start/stop (`context.tracing.start()` /
`context.tracing.stop({ path: ... })` in the `finally` block) so failures remain debuggable without
reverting the hostname workaround.
