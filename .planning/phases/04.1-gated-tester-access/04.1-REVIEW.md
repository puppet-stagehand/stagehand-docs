# Phase 04.1: Code Review Report

**Reviewed:** 2026-08-29
**Depth:** standard
**Files Reviewed:** 22 (`eslint.config.js` was in the declared scope but contains only the
mechanical `.scale-dist/**` ignore-list fix already covered by `04.1-04-SUMMARY.md`; no
additional findings there)
**Status:** issues_found

## Summary

This phase's edge-gating logic (`redirect.js`, `kvs.tf`, `gated-paths.json`) is well-commented,
fails closed on KVS errors, and is exercised by a solid `redirect.test.mjs` suite. The known,
user-accepted D7/AUTH-06 gap (site-wide `enable_basic_auth` blocking the guide's own assets
pre-launch) is **not** re-reported here, per instructions.

However, review surfaced one **additional, undocumented defect in the same area** that is
independent of that accepted gap and will *not* automatically resolve when Phase 05 removes
`enable_basic_auth`: the client-side visibility toggle (`TesterGuideVisibility.astro`) fails
**open**, not closed — any browser that never runs its script, for any reason, shows the
tester-guide content by default rather than hiding it. That is a distinct root cause from the
asset-blocking issue and was not covered by the user's Option-1 decision.

Additional findings: the `visibleOn` content field is defined by the schema as a configurable
per-page channel list but is completely ignored by the code that's supposed to honor it (a latent
bug for the next content author); `isGatedPath()`'s prefix match has no path-boundary check;
there is no test exercising the actual production configuration (gated path + `enable_basic_auth`
both active); there is no test at all — unit or e2e — of `TesterGuideVisibility.astro`'s DOM
behavior; and the KVS store holding the out-of-band tester credential has no `lifecycle` guard
against accidental Terraform-driven replacement.

## Critical Issues

### CR-01: Tester-guide visibility toggle fails open, not closed — a defect independent of the accepted D7/AUTH-06 gap

**File:** `src/components/TesterGuideVisibility.astro:20-26`
**Issue:** The toggle's own comment states the design explicitly:

```js
// Default rendered state is "guide visible, fallback hidden" — matches what a
// testpilots/beta visitor should see, and what every visitor sees if this script
// never runs at all (JS disabled). Only flip state for a disallowed channel.
if (!allowed) {
  guide?.setAttribute('hidden', '');
  fallback?.removeAttribute('hidden');
}
```

`DocsLayout.astro:59-69` server-renders the guide body visible and the fallback `hidden` by
default, and only this script — running client-side, after hydration, only if it loads and
executes without error — ever flips that state for a `stable` (or unknown) channel.

The phase's own close-out (`04.1-04-SUMMARY.md`, check 6 / D7) documents and the user accepted
*one specific cause* of this script not running: the pre-launch `enable_basic_auth` lockdown
blocking the script's own asset request. That is correctly out of scope to re-report here.
But the fail-open *design* is a broader, independent defect that persists even after Phase 05
removes `enable_basic_auth`: any tester whose browser doesn't execute this script for *any other*
reason — JavaScript disabled, an extension or corporate policy blocking third-party or all
scripts, a slow/flaky connection where the page is read before hydration completes, `curl`/text
browsers, or simply a JS runtime exception thrown before this snippet runs — will see the full
guide body on `stable` instead of the fallback message. This was not evaluated or accepted as a
risk in the Decision Resolved section; that section frames the problem as fully explained by, and
expected to "resolve automatically... with zero code change" once, the asset-blocking issue is
gone. That claim is only true for the one specific cause investigated; the no-JS-by-any-cause
case was not tested or discussed and will still misbehave post-Phase-05.
**Fix:** Invert the default so the mechanism fails closed for the case it's actually trying to
protect (hiding pre-release content from `stable`). Two viable options, either fixes this without
touching the accepted D7/AUTH-06 boundary:
```astro
<!-- Option A: render nothing server-side; script must run to reveal content -->
<div class="docs-content" data-tester-guide hidden>
  <slot />
</div>
<p data-tester-guide-unavailable>...</p>
<script>
  const guide = document.querySelector<HTMLElement>('[data-tester-guide]');
  const fallback = document.querySelector<HTMLElement>('[data-tester-guide-unavailable]');
  const allowed = resolveSiteChannel(window.location.hostname) === 'testpilots' ||
    resolveSiteChannel(window.location.hostname) === 'beta';
  if (allowed) {
    guide?.removeAttribute('hidden');
    fallback?.setAttribute('hidden', '');
  }
</script>
```
This means a non-JS visitor sees the safe fallback everywhere, and only a working toggle on an
allowed channel reveals the guide — the correct fail-safe direction for content meant to be
hidden from `stable`.

## Warnings

### WR-01: `visibleOn` frontmatter field is defined but never actually consulted

**File:** `src/content.config.ts:12`, `src/layouts/DocsLayout.astro:59,63,94`,
`src/components/TesterGuideVisibility.astro:18`
**Issue:** `content.config.ts` defines `visibleOn` as `z.array(z.enum(['testpilots', 'beta',
'stable'])).optional()` — an explicit, per-page, arbitrary-combination channel list.
`testers-guide.md` sets `visibleOn: ['testpilots', 'beta']`, but nothing in the render path ever
reads that array's actual values. `DocsLayout.astro` only checks *truthiness*
(`entry.data.visibleOn ? true : undefined`, `entry.data.visibleOn && (...)`), and
`TesterGuideVisibility.astro` hardcodes the allowed set itself
(`channel === 'testpilots' || channel === 'beta'`) with no prop passed in at all. Today this
happens to work only because the one page using the field has exactly the values the hardcoded
check expects. Any future content author who authors a second gated doc with, say,
`visibleOn: ['beta']` only, or `visibleOn: ['stable']`, will get silently wrong behavior — the
schema promises per-page configurability the implementation doesn't deliver.
**Fix:** Pass the entry's actual channels into the component and check membership against them
instead of a hardcoded literal:
```astro
<!-- DocsLayout.astro -->
{entry.data.visibleOn && <TesterGuideVisibility allowedChannels={entry.data.visibleOn} />}
```
```astro
<!-- TesterGuideVisibility.astro -->
interface Props { allowedChannels: string[] }
const { allowedChannels } = Astro.props;
<script define:vars={{ allowedChannels }}>
  const allowed = allowedChannels.includes(resolveSiteChannel(window.location.hostname));
  ...
</script>
```

### WR-02: `isGatedPath()` prefix match has no path-boundary check

**File:** `infra/modules/static-site/functions/redirect.js:41-48`
**Issue:** `uri.indexOf(prefixes[i]) === 0` matches any URI that merely *starts with* the
declared string, not just the declared path and its `/`-delimited sub-paths. With the current
single entry `/docs/testers-guide`, a future, unrelated content page whose slug happens to share
that prefix — e.g. `/docs/testers-guide-faq` or `/docs/testers-guideline` — would be silently
swept into the tester gate and require the shared tester credential to view, with no error or
warning at build or deploy time. `redirect.test.mjs` proves prefix matching covers *intended*
nested sub-paths (`/docs/testers-guide/setup`) but has no test for this false-positive case.
**Fix:** Require the match to land on a path boundary:
```js
function isGatedPath(uri, prefixes) {
  for (var i = 0; i < prefixes.length; i += 1) {
    var prefix = prefixes[i];
    if (uri === prefix || uri.indexOf(prefix + '/') === 0) {
      return true;
    }
  }
  return false;
}
```

### WR-03: No test exercises the actual production configuration — gated path with `enable_basic_auth` also enabled

**File:** `infra/modules/static-site/tests/redirect.test.mjs`
**Issue:** All three real environments (`testpilots`, `beta`, `stable`) run with
`enable_basic_auth = true` *and* a non-empty `gatedPathPrefixes` simultaneously — that is the
only configuration ever actually deployed. Every gated-path test in this file calls
`loadFunction(false, false, gatedPaths, ...)` (`basicAuthEnabled` hardcoded `false`), and the one
test that sets `basicAuthEnabled = true` (`'non-gated path is unaffected by the new gate...'`)
exercises a *non-gated* path. No test proves that, with both mechanisms enabled together, a
request to the gated path carrying only the tester credential (not the basic-auth credential)
still succeeds, and vice versa. The mutual-exclusivity guarantee this whole feature depends on
(D-05/D-06) is only proven for configurations that don't match what's actually deployed.
**Fix:** Add a case such as:
```js
test('gated path with both mechanisms enabled: tester credential succeeds without the basic-auth credential', async () => {
  const gatedContext = loadFunction(false, true, gatedPaths, {
    gate_expected_header: gateExpectedHeader,
  });
  const result = await gatedContext.handler(
    request(
      '/docs/testers-guide/',
      'testpilots.puppet-stagehand.com',
      {},
      { authorization: { value: gateExpectedHeader } },
    ),
  );
  assert.equal(result.uri, '/docs/testers-guide/index.html');
});
```

### WR-04: `TesterGuideVisibility.astro`'s actual DOM behavior has zero test coverage

**File:** `src/components/TesterGuideVisibility.astro`, `tests/unit/site-channel.test.ts`,
`tests/e2e/*`
**Issue:** `site-channel.test.ts` only unit-tests the pure `resolveSiteChannel()` function.
Nothing — no unit test, no Playwright e2e spec (`tests/e2e/` has no `testers-guide`-related spec
at all) — exercises the component's actual `querySelector`/`setAttribute`/`removeAttribute`
logic against real rendered markup. A typo in either `data-*` selector, a wrong attribute name,
or an inverted condition in the `if (!allowed)` branch would ship undetected; this is exactly the
class of bug CR-01 above falls into, and the test suite would not have caught it.
**Fix:** Add a component-level test (e.g. via `@astrojs/*` render helpers or a jsdom-based test
that imports the built script and stubs `window.location.hostname`) asserting `hidden` toggles
correctly for `testpilots`/`beta`/`stable`/unknown hostnames, and consider an e2e spec that
overrides `window.location.hostname` (via `page.addInitScript`) before navigating to
`/docs/testers-guide/` in the local dist server.

### WR-05: `aws_cloudfront_key_value_store.tester_gate` has no protection against accidental Terraform-driven replacement

**File:** `infra/modules/static-site/kvs.tf:1-5`
**Issue:** `docs/operations/tester-access.md` states the KVS's *value* deliberately lives outside
Terraform's management surface, seeded and rotated only via `aws cloudfront-keyvaluestore
put-key`. That means if a future Terraform change ever forces replacement of this resource (e.g.
a rename, or any other `ForceNew` attribute change), Terraform will destroy and recreate the
store with no data — since Terraform never held the credential, it cannot restore it — silently
locking every tester out until an operator notices and re-seeds it by hand. Nothing in the
resource itself guards against this; the safety is entirely prose-only, in a separate doc file.
**Fix:**
```hcl
resource "aws_cloudfront_key_value_store" "tester_gate" {
  name    = "stagehand-${var.environment}-tester-gate"
  comment = "..."
  tags    = local.required_tags

  lifecycle {
    prevent_destroy = true
  }
}
```

### WR-06: Tester-gate credential rotation has no strength/format enforcement, unlike the sibling `enable_basic_auth` credential

**File:** `docs/operations/tester-access.md:29-44`
**Issue:** `variables.tf`'s `basic_auth_password` has a Terraform `validation` block requiring at
least 12 characters. The tester-gate credential documented here is rotated entirely outside
Terraform via a raw `aws cloudfront-keyvaluestore put-key` call with no equivalent guard — an
operator following this runbook exactly as written can set `NEW_PASSWORD` to an empty string or a
single character and the documented commands will happily encode and deploy it live within
seconds, with no warning.
**Fix:** Add a minimum-length check to the documented rotation snippet (or a small wrapper
script) before the `put-key` call, e.g.:
```sh
[ "${#NEW_PASSWORD}" -ge 12 ] || { echo 'NEW_PASSWORD must be at least 12 characters' >&2; exit 1; }
```

## Info

### IN-01: Non-constant-time credential comparison in `redirect.js`

**File:** `infra/modules/static-site/functions/redirect.js:86,93`
**Issue:** Both the tester-gate check (`gateAuthHeader.value !== expectedGateHeader`) and the
basic-auth check (`authHeader.value !== '__BASIC_AUTH_EXPECTED_HEADER__'`) use JavaScript's
built-in `!==`, which short-circuits on the first differing character. CloudFront Functions'
restricted runtime has no `crypto.timingSafeEqual` equivalent, and the practical exploitability
of a timing side-channel through CloudFront's edge network and normal internet jitter is very
low, but it's worth a documented, deliberate acceptance rather than an unstated default the way
the KVS fail-closed behavior is already commented.
**Fix:** Either add a brief comment noting this was considered and accepted (matching the style
already used elsewhere in this file for other tradeoffs), or implement a simple fixed-time
compare loop if this ever needs to be hardened further.

### IN-02: Rotation runbook doesn't document the `--if-match` conflict path

**File:** `docs/operations/tester-access.md:46-57`
**Issue:** The documented rotation flow fetches an `ETag` and writes with `--if-match "$ETAG"`,
which is good practice (prevents blind overwrites), but the doc never tells the operator what a
failed `put-key` (ETag mismatch, e.g. from a concurrent rotation) looks like or that the fix is
simply to re-fetch the `ETag` and retry from step 2.
**Fix:** Add one sentence noting that a `PreconditionFailed`/ETag-mismatch error means someone
else changed the value concurrently, and the remedy is to re-run the `describe-key-value-store`
fetch and retry the write.
