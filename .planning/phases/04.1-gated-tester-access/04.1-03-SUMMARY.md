- **Issue:** `tests/unit/deploy-scripts.test.ts` asserts the exact `cloudfront create-invalidation
  --paths` command string produced by `deploy-site.sh`; adding the new path without updating this
  test's expected string fails the suite.

**2. [Rule 1 - Bug] Fixed CSP-defeating script inlining via `astro.config.mjs`**
- **Found during:** Task 3, verifying the acceptance criterion "no `is:inline` directive or inline
  event-handler attribute is introduced" by inspecting the actual built `dist/` output (not just
  trusting the source-level absence of `is:inline`)
- **Issue:** The visibility script has no `is:inline` directive and no inline event handler in the
  source, matching the plan's literal requirement — but Vite's default small-asset inlining
  (`assetsInlineLimit`, default 4096 bytes) was compiling the script and then inlining its content
  directly into the page HTML as literal `<script type="module">...</script>` text (no `src=`
  attribute) because the compiled, tree-shaken chunk was small and self-contained. This site's CSP
  is `script-src 'self'` with no `'unsafe-inline'`/nonce/hash — an inline script executes only
  with an exception; a strict CSP without one silently blocks it at runtime, with zero build-time
  error. This is functionally the identical failure Pitfall 6 in RESEARCH.md warned about for
  `is:inline`, just triggered by chunk size rather than an explicit directive — a real correctness
  bug the plan's own threat model implicitly assumes doesn't happen.
- **Fix:** Set `vite.build.assetsInlineLimit: 0` in `astro.config.mjs`, with an inline comment
  explaining why. Rebuilt and confirmed in `dist/docs/testers-guide/index.html`: the script is now
  `<script type="module" src="/assets/TesterGuideVisibility.astro_astro_type_script_index_0_lang.*.js">`
  — external, same-origin, present only on that one page.
- **Files modified:** `astro.config.mjs`
- **Verification:** Rebuilt `dist/`, grepped the output HTML for both `docs/testers-guide/` (has
  the external `<script src>`) and `docs/security/` (has no script at all); re-ran `npm run
  check:routes`, `npm run check:invalidation`, `npx astro check`, and the full `npx vitest run`
  suite — all green.
- **Committed in:** `84be364` (Task 3 commit)

### Structural adjustment (not a deviation from behavior, but from literal plan text)

The plan's Task 3 action describes emitting the `<script>` block directly inside
`DocsLayout.astro`'s conditional expression, immediately after `</article>`. I implemented this as
a separate `TesterGuideVisibility.astro` component, conditionally rendered from that same location,
because prettier's Astro parser cannot format a `<script>` tag nested inside a `{cond && (...)}`
JS expression (confirmed via isolated repro — `astro build`/`astro check` both succeed regardless,
but `prettier --check` throws a hard parse error, which would fail `npm run verify`'s
`format:check` step). The functional result is identical: the script is still emitted only on
pages where `entry.data.visibleOn` is set, still non-`is:inline`, still reads
`window.location.hostname` via `resolveSiteChannel`. Documented here for transparency since it's a
structural deviation from the plan's literal file-layout description, even though the plan's
`files_modified` list (`src/layouts/DocsLayout.astro`) and all acceptance criteria are satisfied.
