## Decisions Made

- **Mutually-exclusive `if`/`else-if` gate placement** (not two independently-evaluated checks):
  both the new gate and the pre-existing whole-site `enable_basic_auth` lockdown read the same
  shared `Authorization` header, and a browser can only send one value — evaluating both would
  conflate two credentials D-06 requires stay separate. A gated path is now protected
  *exclusively* by the new tester password; every other path keeps the pre-existing
  `enable_basic_auth` behavior, completely unaffected. This is documented as reversible in the
  plan (`<reversibility rating="reversible">`) — restructurable later without any external API
  change.
- **KVS stores a complete precomputed `"Basic " + base64(":<password>")` header value**, not a
  raw password — mirrors the existing `basic_auth_expected_header` local's exact technique,
  meaning the function does a single string comparison with no base64-decoding of the incoming
  header, avoiding a second unverified CloudFront Functions runtime API surface on top of the
  already-flagged `cf.kvs()` one.
- **Fail-closed on any KVS lookup failure**: the `try`/`catch` around `cf.kvs().get(...)` returns
  `unauthorized()` on any thrown error (missing key, KVS outage, or unexpected runtime error) —
  never falls through to serving gated content. This is the STRIDE T-04.1-02 mitigation.
