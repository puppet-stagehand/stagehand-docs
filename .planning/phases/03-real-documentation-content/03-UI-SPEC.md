# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** Phase 3 is primarily a content phase — the visual system is already fully
established and shipped in the scaffold (Astro static site, Bootstrap 5 via Sass, dark
"control-plane / register" aesthetic). This contract's job is to say **reuse, don't reinvent** for
everything that already exists, and to be prescriptive about the small number of genuine gaps this
phase's real content will expose (a home-page tier path, a support-page lifecycle section, and
markdown code-block styling that has never been needed until now).

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — Astro static site, no component-generation tool. shadcn does not apply (React-only tool; this project ships zero client-side framework). |
| Preset | not applicable |
| Component library | Bootstrap 5.3.8 via Sass (`src/styles/global.scss`), heavily overridden — only `functions`, `variables`, `maps`, `mixins`, `utilities`, `root`, `reboot`, `containers`, `grid`, `nav`, `navbar`, `tables`, `badge`, `accordion`, `buttons`, `forms`, `helpers`, `utilities/api` partials are imported. Bootstrap's `code` partial is **not** imported (see Docs section — this is a real gap this phase surfaces). |
| Icon library | none — no icon font/SVG sprite system. The existing UI uses typographic marks instead of icons: mono-uppercase index numerals (`01`, `02`...), `→`/`↓` glyph characters, and CSS-drawn indicators (`.status-mark__indicator`, corner brackets). New content must follow this convention, not introduce an icon library (would also risk a third-party asset, which CONT-06 forbids unless self-hosted and reviewed). |
| Font | IBM Plex Sans (body/headings, self-hosted via `@fontsource/ibm-plex-sans`, weights 400/600 loaded) and IBM Plex Mono (labels/eyebrows/buttons/code, self-hosted via `@fontsource/ibm-plex-mono`, weight 400 loaded). Gibson is explicitly out of scope (unresolved embedding licence). |

**Detected, not decided:** every value in this document below was read directly out of
`src/styles/_tokens.scss`, `src/styles/global.scss`, `src/styles/components/*.scss`, and the
rendered `.astro` pages/components — not proposed fresh. Phase 3 plans and executor work must
extend these tokens and reuse these component classes; introducing a second visual language for
new content is out of contract.

## Spacing Scale

Declared values (must be multiples of 4), read from the shipped component styles:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-adjacent gaps (`status-mark` indicator gap fractions), 1px accent-line offsets |
| sm | 8px | Compact element spacing (`gap: 0.5rem`, list item gaps) |
| md | 16px | Default element spacing (card padding on mobile, `gap: 1rem`) |
| lg | 24px | Section-internal spacing (`gap: 1.5rem`, mobile card padding upper bound) |
| xl | 32px | Layout gaps (`gap: 2rem`, footer grid gap) |
| 2xl | 48px | Major section breaks (`tier-enforcement` vertical padding, capability card lower padding) |
| 3xl | 64px | Page-level spacing (desktop hero rail padding, `docs-shell__rail` top padding) |

Exceptions:
- **Fluid section rhythm via `clamp()` is an established, intentional pattern** — e.g.
  `padding: clamp(4rem, 8vw, 7rem) 0` on `.docs-index`/`.support-page`,
  `clamp(3.5rem, 8vw, 6.5rem)` on `.tier-intro`. These are not fixed-token spacing; they are
  responsive section padding. **New sections (the home tier CTA, the support lifecycle block)
  must reuse an existing section's `clamp()` call rather than invent a new one.**
- Intermediate 4px-grid values already in shipped CSS that don't map to a named token above (e.g.
  `0.75rem`/12px nav link padding, `1.25rem`/20px eyebrow margin, `1.75rem`/28px tier register
  padding, `2.5rem`/40px card padding upper bound) are permitted — they stay on the 4px grid, they
  are simply un-named intermediate steps. Do not round these away when reusing existing classes.

## Typography

The shipped system is **fluid/clamp-based by established convention**, not fixed-pixel. The table
below gives the representative anchors already in production CSS; new content reuses the existing
selectors (`h1`/`h2`/`h3`, `.section-kicker`, `.docs-content p`) rather than declaring new sizes.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px (`$font-size-base: 1rem`) | 400 (regular) | 1.6 (`$line-height-base`) |
| Label (mono eyebrow/kicker/nav/index numerals) | 11px (`0.6875rem`) | 400 | 1.0, uppercase, `letter-spacing: 0.08–0.15em`, IBM Plex Mono |
| Heading (h2/h3 section and article headings) | Fluid, representative anchor 32–60px (`clamp(2rem, 5vw, 3.75rem)` pattern; article `h1` uses `clamp(2.5rem, 6vw, 5rem)`) | 600 (`$headings-font-weight`) | 1.05 (`$headings-line-height`), `letter-spacing: -0.025em` to `-0.055em` at larger sizes |
| Display (hero H1 / oversized numeral marks) | Fluid, anchor 52–116px (`clamp(3.25rem, 8vw, 7.25rem)` on the home hero) | 600 | 1.05 (0.75 for the oversized `.not-found__code` numeral only) |

Only 2 weights exist in the loaded font files (400, 600) — do not introduce a third weight; if a
markdown author reaches for **bold** inline text, it renders at 600 (`<strong>`/`<b>` inherit
`headings-font-weight` is not automatic in body text — confirm `<strong>` renders at whatever the
browser bold-weight fallback resolves to, since only 400/600 files are loaded; this is already the
shipped behavior and out of scope to change this phase).

## UI Considerations

Applicable state considerations resolved: 7 covered, 1 backstop, 2 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Tiers list (`TierCard` × `loadTiers()`, list-collection) | ✅ covered | `src/data/schema/tiers.schema.json` + `assertExactTierSet` require exactly the four tier IDs (`openvox`, `puppet-core`, `puppet-enterprise`, `pe-advanced`); a missing tier throws at build. An empty tiers list can never reach render — no runtime empty-state UI is needed or should be built. |
| empty | Docs index list (`getCollection('docs')`, list-collection) | ✅ covered | CONT-04 requires the collection to carry real, reviewed operator content this phase; entries are git-committed structured data, not user input. A zero-entry build is a content-authoring failure to catch in review, not a state the UI needs to render gracefully. |
| loading | All list/nav/interactive elements site-wide (list-collection, nav, interactive-control) | ✅ covered | `output: 'static'` — no client-side data fetching exists anywhere. CONT-06 additionally forbids third-party runtime scripts. No loading state exists or is permitted in this project. |
| error | All list/nav/interactive elements site-wide (list-collection, nav, interactive-control) | ✅ covered | Same static-site boundary as loading — invalid data fails the *build* (fail-closed schema validation), never renders a partial or error UI at runtime. The only runtime error surface is the existing branded `404.astro`, unchanged this phase. |
| populated | Docs index list at realistic guide count (list-collection) | 🧪 backstop | `.docs-index__list` is an unbounded bordered-row list with no hardcoded item cap, but CONT-04 grows entries from the current 2 to a realistic first-run/security/trust-boundary guide set this phase. Visually verify the list (row rhythm, `docs-index__order` alignment, total scroll length) once the real entry count is known — no explicit test currently asserts appearance at volume. |
| partial | Tier + docs data records (list-collection) | ✅ covered | Both loaders (`loadTiers()` here, and the shared `loadYaml`/schema pattern used by `loadCompatibility()`) are fail-closed against a JSON Schema with `additionalProperties: false` and required fields — a malformed or partially-filled record throws at build rather than rendering with missing fields. |
| overflow | Docs sidebar nav (`DocsNavigation.astro`, nav) at growing entry count | ⚠ unresolved | `.docs-nav ol` (`display: grid; gap: 0.25rem`) has no `max-height` or scroll affordance. As CONT-04 adds guide entries this phase, a long rail list next to a short article body has no defined behavior. Planner should decide — once the real guide count is known — whether the current unbounded list stays acceptable (fine at roughly 5–8 entries, matching the two-column `docs-shell__grid` proportions) or needs a `max-height` + `overflow-y: auto` addition. Treated as an explicit planner assumption if left unresolved. |
| overflow | Markdown code blocks / inline code in `.docs-content` (static-content) | ⚠ unresolved | **No `pre`/`code`/`kbd` styling exists anywhere in `src/styles`** — Bootstrap's `code` partial is not among the imported partials in `global.scss`. A first-run or security guide that includes an SSH command, a YAML snippet, or an inline flag (all realistic for CONT-04's "install, first-run, trust boundaries" content) will render with unstyled browser-default monospace, no defined foreground color for the dark theme (default black-on-transparent is close to invisible on `--stagehand-navy`), and no `overflow-x` handling for a long single-line command. | zero-one-many | Tier `features` list per `TierCard` (list-collection) | ⚠ unresolved | `tiers.schema.json`'s `features` array has no `minItems` — a tier record with zero features would pass validation and render an "INCLUDED SCOPE" heading over an empty `<ul>`. Flagging here rather than tightening the schema, since schema changes are outside a content phase's blast radius unless the planner decides otherwise. |
| long-text | Home hero H1 headline (static-content) | ✅ covered | `.control-hero h1` already constrains to `max-width: 12ch` with fluid `clamp()` sizing and no truncation; new positioning copy (CONT-01) must fit that width budget — the existing wrap behavior handles any length within reason, no new CSS needed. |
| long-text | Tier audience/summary copy (static-content, data-driven) | ✅ covered | `.tier-register__body > p` already caps at `max-width: 42rem`; variable-length real entitlement copy (replacing the current one-line placeholders) wraps naturally under the existing rule. |

## Page-Specific Contracts

### Home (`/`)

Reuse `.control-hero` + `.capabilities` sections unchanged structurally. Content-only changes
except the one addition below:

- **Hero actions row** (`.control-hero__actions`): add the "View tiers" secondary CTA (see
  Copywriting Contract) as the second of three buttons: Get started (`.btn.btn-primary`) → View
  tiers (`.btn.btn-outline-light`) → Check compatibility (`.btn.btn-outline-light`). The row
  already `flex-wrap: wrap`s at narrow widths — three buttons wrap to a stacked column on mobile
  without new CSS.
- **Capability grid** (3 cards): copy-only rewrite to real product positioning language (currently
  placeholder-grade: "Environment visibility", "Bolt-native execution", "Explicit support
  boundaries"). Card count, index-numeral pattern (`01`/`02`/`03`), and grid layout are unchanged.
  Do not add a 4th card without also updating the 3-column desktop grid CSS (`grid-template-columns: repeat(3, ...)` in `_shell.scss`).
- **Hero rail data points** (`CONTROL MODE` / `EXECUTION` `StatusMark`s): copy-only if changed;
  keep the two-datum grid, do not add a third without extending `.control-hero__rail`'s
  `grid-template-columns: repeat(2, ...)`.

### Tiers (`/tiers/`)

No structural change. `TierCard.astro` + `loadTiers()` already renders exactly 4 tiers from
`src/data/tiers.yaml` in the established register-list layout. This phase's work is entirely data
content:

- `summary` and `audience` per tier: rewrite to real, comparative, customer-facing entitlement
  language (CONT-02) — currently one-line placeholders ("Community-oriented deployments using
  OpenVox.").
- `features` per tier: expand from the current single placeholder bullet to a real, comparative
  feature/entitlement list. **Minimum 1 item required** (see UI Considerations — zero-one-many,
  unresolved).
- `tier-intro__levels` dl block (Community/Commercial/Advanced → product mapping) at the top of
  the page: verify the three-way grouping text still matches the real tier copy once `features`
  changes.
- Do not touch `TierCard.astro`, `_tier-card.scss`, or the schema (`tiers.schema.json`) unless a
  planner explicitly decides the `minItems` gap above needs a schema fix — default assumption is
  content discipline, not a schema change.

### Support (`/support/`)

Reuse the existing `register-hero` + `support-page__grid` two-channel layout unchanged. **Add one
new section** to satisfy CONT-03's "states the product lifecycle" clause, which nothing on the
page currently covers:

- **New "Product lifecycle" section**, inserted between `<header class="register-hero ...">` and
  `<section class="support-page" ...>`. Reuse the existing kicker+heading section pattern
  (`.section-kicker` + `<h2>`, matching `.tier-intro`'s structure and vertical rhythm —
  `padding: clamp(3.5rem, 8vw, 6.5rem) 0`, `border-bottom: 1px solid var(--stagehand-line-strong)`,
  background `var(--stagehand-raised-navy)`). Content: current release/lifecycle stage stated in
  customer terms (e.g. what "beta"/"stable" means for this product, without asserting any
  entitlement or premium behavior — CONT-06). If the lifecycle content includes a caution (e.g.
  "PCP/orchestrator behavior is not available yet"), reuse the exact `.support-page__warning`
  callout pattern (amber left-border, 8%-opacity tint) already used lower on the page — don't
  invent a second warning treatment.
- The two existing channel cards (public project / commercial product) are copy-stable; only
  update if the lifecycle addition changes what belongs in "where to report."

### Docs (`/docs/` index + `/docs/[...slug]/`)

No new route files or layout components — `DocsLayout.astro`, `DocsNavigation.astro`, and the
dynamic `getStaticPaths()` in `[...slug].astro` already handle any number of content-collection
entries. CONT-04's work is entirely new markdown files under `src/content/docs/`, each with
required frontmatter (`title`, `description`, positive unique `order`, optional `updated` —
enforced by `src/content.config.ts`'s Zod schema).

**New — Docs Code Block Contract (required before any doc ships a command/snippet):**

Add to `src/styles/components/_docs.scss`, scoped under `.docs-content` so it only affects
rendered markdown prose (not the mono labels elsewhere on the site, which already have their own
rules):

```scss
.docs-content pre {
  margin: 1.5rem 0;
  padding: 1rem 1.25rem;
  overflow-x: auto;
  border: 1px solid var(--stagehand-line-strong);
  background: var(--stagehand-raised-navy);
  color: var(--stagehand-off-white);
  font-family: var(--stagehand-mono);
  font-size: 0.875rem;
  line-height: 1.6;
  white-space: pre;
}

.docs-content code {
  padding: 0.15em 0.4em;
  border: 1px solid var(--stagehand-line);
  background: rgba(32, 215, 231, 0.08);
  color: var(--stagehand-off-white);
  font-family: var(--stagehand-mono);
  font-size: 0.875em;
}

.docs-content pre code {
  padding: 0;
  border: 0;
  background: none;
}
```

Rationale for the exact values: `--stagehand-raised-navy` block background and
`--stagehand-off-white` foreground reuse the existing secondary-surface color pair (same pairing
as capability/support cards), so code blocks read as another "raised" surface rather than a new
color language. The inline-code tint (`rgba(cyan, 0.08)`) reuses the exact opacity already used for
`.docs-nav a:hover`'s background, keeping the cyan accent's 10%-budget consistent. `overflow-x: auto`
on `pre` is the fix for the unresolved long-text/overflow finding above. Run axe (CONT-07) against
a doc page containing both an inline `<code>` span and a `<pre>` block once real content lands —
this pairing has never been contrast-checked in this codebase because it has never existed.

**Docs breadcrumbs, pagination, and sidebar nav:** unchanged structurally; verify the sidebar
overflow question above once the real guide count from CONT-04 is known.

## Accessibility Requirements (CONT-07)

Matches the existing, already-passing `tests/e2e/accessibility.spec.ts` contract exactly — this
phase's content must not regress it, and any new doc pages should be added to the audited-route
set at the planner's discretion (currently only `/docs/` index is audited, not individual
`/docs/[slug]/` pages):

- **Axe:** zero `serious`/`critical` violations, tag set `['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa']`, on `/`, `/tiers/`, `/compatibility/`, `/docs/`.
- **Landmarks:** exactly one `banner` (site header), one `main`, one `contentinfo` (site footer) per page — already provided by `BaseLayout.astro`; do not wrap new sections in a competing landmark role.
- **Heading order:** exactly one `<h1>` per page. New sections added this phase (home CTA row, support lifecycle block) must use `<h2>`/`<h3>`, never a second `<h1>`.
- **Skip link:** `Skip to main content` → `#main-content`, already shipped in `BaseLayout.astro`, unchanged.
- **Keyboard operability + visible focus:** `:focus-visible { outline: 2px solid var(--stagehand-warning); outline-offset: 4px; }` is global — new interactive elements (the "View tiers" link, any new doc-page internal links) inherit this automatically as long as they are real `<a>`/`<button>` elements, not `div`s with click handlers (which CONT-06 would also forbid as client-side behavior beyond native anchors).
- **Color-independent status:** existing pattern (`StatusMark`) already pairs a CSS-drawn indicator glyph with a text label — reuse this if any new lifecycle-status copy needs a status-like treatment; never convey lifecycle stage by color alone.
- **Language:** `<html lang="en">`, unchanged.

## Forbidden Patterns (CONT-06)

Explicit boundary this phase's content must not cross, regardless of how natural it might read in
a first-draft of documentation or marketing copy:

- **No credential collection.** No form fields for SSH keys, tokens, passwords, or API credentials anywhere in new content or pages.
- **No entitlement assertion UI.** No "Your plan includes..." personalization, no login-gated content preview, no client-side tier detection. The existing pattern is descriptive-only ("this register describes content boundaries; it does not grant or enforce product access" on `/tiers/`) — new content follows the same descriptive, non-assertive voice.
- **No third-party runtime script.** No embedded video players, no analytics/telemetry beacons, no CDN-hosted widgets (chat, feedback, cookie banners). CSP is self-hosted-assets-only; this is a hard build/security constraint, not a style preference.
- **No analytics.** Deliberately deferred project-wide; do not add page-view tracking, event tracking, or any pixel — including "privacy-friendly" self-hosted options, which are out of scope until a future privacy/retention decision.
- **No premium-feature UI presented as shipped.** Specifically: no docs page, home capability card, or support-lifecycle copy may present Puppet Console workflows, PCP/orchestrator behavior, or entitlement enforcement as available today. The existing `getting-started.md`/`security.md` language ("Premium PCP/orchestrator behavior is unavailable until an approved Stagehand release compatibility record documents it. Do not treat planned integration language as evidence that the behavior ships today.") is the model voice — new content must match this discipline, not soften it into implied availability.
- **No download/installer UI this phase.** `/downloads/`, docker-pull commands, and installer links belong to Phase 04.2 (`DOWN-01`–`DOWN-04`), which is gated behind Phase 04.1's shared-password edge auth. Phase 3 content must continue treating installation as "prepare an OpenVox environment + SSH" only, matching the current `getting-started.md` scope — do not pre-announce a download path that doesn't exist yet.
