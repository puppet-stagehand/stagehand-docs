<objective>
Build the dedicated, reusable GATE-03 regression test: a script that fails when a route present in a
real built site is missing from `scripts/deploy-site.sh`'s CloudFront invalidation list, wired into
`npm run verify` so the failure is a build-time gate, not a discovery in production. This is the
mechanical safety net that makes CONT-05's "register in the same change" discipline enforceable for
every future documentation page this repository ever adds — not just the one 03-01 adds this phase.

Purpose: GATE-03's exact text is "a test fails when a route present in the built output is missing from
the invalidation list in `scripts/deploy-site.sh`." No such test exists yet — `tests/unit/deploy-scripts.test.ts`
only proves the *current* invalidation list produces the expected AWS CLI invocation via one hardcoded
literal string; it does not compare that list against the real built output, so a future contributor who
forgets to add an invalidation entry for a new page would see `npm run verify` stay green.
Output: `scripts/check-invalidation-coverage.ts` (new script, mirrors `scripts/check-built-routes.ts`'s
pattern), `tests/unit/invalidation-coverage.test.ts` (new unit test, mirrors `tests/unit/built-routes.test.ts`'s
synthetic-fixture pattern), and a new `check:invalidation` npm script wired into the `verify` chain.
</objective>

  <action>
    Implement `scripts/check-invalidation-coverage.ts` as a standalone CLI script mirroring
    `scripts/check-built-routes.ts`'s structure: reads `buildRoot` from `process.argv[2]` (default
    `'dist'`) and `deployScriptPath` from `process.argv[3]` (default `'scripts/deploy-site.sh'`). Logic:
    (1) read the deploy script's text and, from the substring after the `--paths` marker, extract every
    single-quoted, `/`-prefixed token via a regex matching `'(\/[^']*)'`; (2) split those into literal
    paths (exact strings not ending in `*`) and glob prefixes (strings ending in `*`, matched by
    `route.startsWith(prefix.slice(0, -1))`); (3) recursively walk `buildRoot`, collecting the web path
    (leading `/`, POSIX separators) of every `*.html` file, skipping any directory literally named
    `assets`; (4) return the list of collected routes that match neither a literal path nor a glob
    prefix. If that list is non-empty, throw an `Error` listing each missing route (same message shape
    as `check-built-routes.ts`'s thrown error); if empty, `console.log` a one-line confirmation naming
    how many routes were verified. Export the core walking/matching logic as a named async function
    (e.g. `findMissingInvalidationPaths(buildRoot: string, deployScriptPath: string): Promise<string[]>`)
    so it is unit-testable in isolation later if needed, but the test file from Task 1 exercises it only
    through the CLI (`spawnSync`), matching `built-routes.test.ts`'s existing pattern — do not change the
    test file's invocation style.

    In `package.json`'s `scripts` block, add `"check:invalidation": "node --import tsx scripts/check-invalidation-coverage.ts"`
    immediately after the existing `"check:routes"` entry. In the `"verify"` script's command chain,
    insert `&& npm run check:invalidation` immediately after `&& npm run check:routes` and before
    `&& npm run check:links` — this ordering matters: both `check:routes` and `check:invalidation`
    need `dist/` to exist (produced by the preceding `npm run build` step in the chain) and both are
    fast, build-artifact-only checks that should fail before the slower link-crawl and e2e steps run.
  </action>
