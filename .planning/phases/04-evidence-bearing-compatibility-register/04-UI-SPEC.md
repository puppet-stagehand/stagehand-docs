# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This is not a greenfield UI phase. `src/components/CompatibilityMatrix.astro` and
`src/styles/components/_compatibility.scss` **already implement** a populated-matrix UI —
semantic `<select>` filters, a live result count, text+icon status, and a table→card responsive
collapse — but it has never rendered on a real build, because `src/data/compatibility.yaml` has
always held `records: []` (ADR-0001) and no test exercises it above 5 fixture records. This
contract's job is to **lock the existing implementation as the design of record**, name the two
real gaps it has (an untokenized color, and untested behavior at realistic volume), and specify
exactly how the empty state and the populated state coexist as two permanently-supported, tested
UI states — not a migration from one to the other. Per COMP-02, the *published* register stays
empty this phase; only test fixtures grow.

## Color

Unchanged base palette from Phase 3, plus **one real gap this phase must close**: an untokenized
red used only by the "unsupported" status.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#071521` (`--stagehand-navy`) | Page background — unchanged |
| Secondary (30%) | `#0d2233` (`--stagehand-raised-navy`), `rgba(13,34,51,0.56)` | `.compat-filters select` fill, `.compat-table thead th` background, `.compat-table caption` (`#06111b`), `.compat-card` surface tint |
| Accent (10%) | `#20d7e7` (`--stagehand-cyan`) | Reserved for: `compat-status--supported`/`compat-status--compatible` glyph+text color, `.compat-card` top border (2px), `.compat-empty__code` eyebrow. Same 10%-budget discipline as Phase 3 — never a fill, never body text. |
| Secondary accent | `#6f3cc3` (`--stagehand-purple`) | Not used within the compatibility matrix. Do not introduce it here — it stays reserved for the "Advanced" tier/entitlement hierarchy per Phase 3's contract. |
| Warning | `#ffbd4a` (`--stagehand-warning`) | `compat-status--limited`/`compat-status--deprecated` glyph+text color. This is the *existing* semantic reuse — "limited" and "deprecated" share the caution-amber token, matching Phase 3's "reserved for caution/warning emphasis" rule. |
| **Destructive / danger (gap — formalize this phase)** | `#ff8b8b`, currently a bare hex literal at `_compatibility.scss:266`, used only by `compat-status--unsupported` | This is a real, load-bearing color with no token and no entry in `_tokens.scss`. **Add `$stagehand-danger: #ff8b8b;` and `--stagehand-danger` to `src/styles/_tokens.scss` in the same pattern as the other five color variables, then reference `var(--stagehand-danger)` from `_compatibility.scss` instead of the raw hex.** Reserved for: `compat-status--unsupported` only. Do not repurpose it as a general destructive-action color — this phase (and the site generally) has no delete/destroy affordance; "unsupported" is a claim state, not a destructive action, so this token's *name* is `danger`/status-severity, not a UI "destructive confirmation" color per the Copywriting Contract below. |

**Status is never color-only** (COMP-04, WCAG 1.4.1): every one of the five statuses already
pairs its color with a distinct glyph (`✓`/`↔`/`!`/`◷`/`×`) rendered in `.compat-status__symbol`
plus a visible text label (`Supported`/`Compatible`/`Limited`/`Deprecated`/`Unsupported`) — this is
already correctly implemented in `CompatibilityMatrix.astro` and covered by
`tests/e2e/fixture-matrix.spec.ts`'s "status never relies on color alone" test. Do not weaken this
when adding fixture volume — every new fixture record's status must render through the same
`presentStatus()` helper, never a bespoke color-only badge.

### Realistic-Volume Fixture Requirement (GATE-04)

This is the one genuinely new piece of UI-relevant work this phase adds to the matrix itself. The
UI already handles it structurally; what's missing is data at the volume needed to prove it.

- **Do not grow or repurpose `tests/fixtures/data/compatibility-e2e.yaml`.** ADR-0001 rule 2 locks
  it at five records spanning every status and every tier, loaded under
  `STAGEHAND_E2E_FIXTURES=1`, and it feeds the build-isolation count assertion COMP-03 reworks. A
  second, explicitly-named test-only fixture is required for scale testing — e.g.
  `tests/fixtures/data/compatibility-scale.yaml` — that is never mistaken for either the published
  register or the ADR-0001 e2e fixture. Name it so a future contributor cannot confuse it with a
  real claim (it is not evidence-bearing; its `evidence_url`s should continue the existing fixture
  convention of pointing at this repository's own issue tracker, exactly as the 5-record fixture
  already does for four of its five records).
- **Minimum composition** for the scale fixture, so it actually exercises the states above rather
  than just being "more rows of the same thing":
  - **≥24 records** (target ~30) — enough that the card layout requires real scrolling on a
    320px-wide viewport and the table requires it on a 1280px viewport, proving the matrix reads
    correctly at a volume no current test reaches.
  - **≥10 distinct `platform` values** — so the platform `<select>` itself becomes a realistic
    length list, not a restatement of the 5-record set.
  - **All 4 tier values and all 5 status values represented at least 3 times each** — so every
    filter combination the reviewer might try returns a non-trivial result set, and the result
    count copy ("Showing N of M verified records") is exercised at multiple N/M pairs, not just
    "1 of 5" and "5 of 5".
  - **A mix of empty and populated `limitations` arrays**, and at least one record with a
    genuinely long `limitations` sentence (60+ characters) and one with an unusually long
    `platform` name, to exercise the backstop wrapping checks above.
  - Every `docs_path` must point at a real, already-shipped route (`/docs/getting-started/`,
    `/docs/security/`, `/docs/first-run/` — confirmed to exist in `src/content/docs/`), matching
    the schema's `^/docs/.+/$` pattern and keeping `check:links` honest.
- **Add an axe scan to the `fixture-matrix` Playwright project.** `tests/e2e/accessibility.spec.ts`
  only runs against the `production` project today (confirmed: no `--project` restriction needed
  because it's the default project, and `fixture-matrix.spec.ts` currently contains zero axe
  assertions) — meaning `/compatibility/` has **never** been axe-scanned in its populated state.
  This is the concrete gap GATE-04 names. Add a test to `fixture-matrix.spec.ts` (or a sibling
  file matched by the same project) that runs `AxeBuilder` with the identical tag set
  (`['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa']`) against `/compatibility/` once it is rendering
  the realistic-volume fixture, asserting zero `serious`/`critical` violations — same bar as every
  other audited route, just never previously applied to the populated matrix.
- **Keyboard operability at volume**: extend (or add alongside) the existing
  `discreteControls` 44px-target loop in `fixture-matrix.spec.ts` to also assert that `Tab` order
  through the realistic-volume table/card set is linear and that every evidence/docs link remains
  reachable — this is a straightforward extension of the existing pattern, not new interaction
  design.

## Page-Specific Contracts

### Compatibility (`/compatibility/`)

No new route, no new layout, no new component files required by this contract — reuse
`CompatibilityMatrix.astro`, `CompatibilityEmptyState.astro`, `_compatibility.scss`, and the
existing `records.length === 0` branch in `index.astro` exactly as shipped. This phase's UI-facing
work is:

1. **Token gap fix**: move `#ff8b8b` into `_tokens.scss` as `$stagehand-danger` /
   `--stagehand-danger` and reference the variable from `.compat-status--unsupported` (see Color).
2. **Fixture volume**: author the realistic-volume scale fixture per the requirement above, and
   wire it into the `fixture-matrix` Playwright project (mechanism — new dist target, new env var,
   or a second `webServer`/project entry — is a build-architecture decision for the planner, not
   prescribed here).
3. **Axe coverage extension**: add the populated-state axe scan described above.
4. **Prose amendments**: land the three DRIFT-04 sentence amendments in the design spec.
5. **Leave the empty-state route path untouched.** `production-empty.spec.ts` continues to be the
   test of record for what a real site visitor sees this phase (COMP-02) — do not delete it, do
   not fold its assertions into the fixture-matrix suite, and do not change
   `CompatibilityEmptyState.astro`'s copy or markup. The empty state and the populated state are
   two permanently-coexisting, separately-tested UI states of the same route, gated by real data
   volume — not a before/after pair where one replaces the other.

**Do not touch** `CompatibilityMatrix.astro`'s markup, filter logic, or breakpoint (`48rem`)
structurally — it already satisfies COMP-04's filterable/visible-count/text+icon/responsive-card
requirements. Any executor temptation to "improve" the matrix while adding fixture data should be
resisted unless a specific backstop item above fails once real volume is rendered.

## Accessibility Requirements (COMP-04, GATE-04)

Matches the site-wide contract already enforced by `tests/e2e/accessibility.spec.ts` and extends it
to the populated state specifically, which has never been covered before this phase:

- **Axe:** zero `serious`/`critical` violations, tag set `['wcag2a', 'wcag2aa', 'wcag21a', 'wcag21aa']`, on `/compatibility/` in **both** its empty state (`production` project, already covered) and its realistic-volume populated state (`fixture-matrix` project, new this phase).
- **Landmarks/heading order/skip link/language:** unchanged from the site-wide `BaseLayout.astro` contract (Phase 3) — the matrix introduces no new landmark and must not introduce a second `<h1>`; `.compat-card__header h2` and table headers stay at their existing heading/`<th>` levels.
- **Color-independent status:** every status renders glyph + text via `presentStatus()` — already implemented, must not regress when fixture volume grows (see Color section).
- **Filter labelling:** all three `<select>` elements keep their implicit wrapping `<label>` (already shipped, already passes `getByLabel()` assertions) — do not switch to placeholder-only or `aria-label`-only labelling.
- **Live region:** the result count keeps `aria-live="polite" aria-atomic="true"` so a screen-reader user filtering a 24–30 record list hears the updated count, not silence — this becomes more load-bearing at realistic volume than it was at 5 records, where the change was easy to notice visually.
- **Keyboard operability + 44px targets:** every `<select>`, "Clear filters", and every evidence/docs link (table and card) keeps `min-height: 2.75rem`; global `:focus-visible { outline: 2px solid var(--stagehand-warning); outline-offset: 4px; }` applies unchanged — verify it remains visible against both the table's dark surface and the card's `rgba(13,34,51,0.56)` tint once real volume is rendered (backstop, not expected to fail).
- **No-JS readability:** `tests/e2e/fixture-matrix.spec.ts` already asserts the table renders correctly with `javaScriptEnabled: false` (filtering degrades gracefully to "show everything," which is correct — a static list is still fully readable without the client-side filter script). Extend this assertion's row-count check to the new realistic-volume record count.

## Forbidden Patterns

Carried forward from Phase 3's CONT-06 boundary — nothing in this phase's fixture or prose work may
cross it:

- **No fabricated customer-facing claims.** The realistic-volume fixture is test data behind
  `STAGEHAND_E2E_FIXTURES=1`-equivalent gating, never promoted into `src/data/compatibility.yaml`
  (COMP-02, ADR-0001 rule 2). If a plan or executor step ever produces a diff touching
  `src/data/compatibility.yaml` to add a non-empty record, that record must have passed the real
  `docs/operations/compatibility-claims.md` review (COMP-01) — it is out of this phase's UI/test
  scope to originate one.
- **No new icon library, no new accent color budget.** The status-glyph pattern and the 10%-cyan
  budget are locked; the one color addition this phase makes (`--stagehand-danger`) formalizes an
  already-shipped, already-scoped usage — it does not open a new general-purpose color.
- **No pagination, virtualization, or infinite scroll.** Not requested by any requirement, and
  introducing one would be new interaction design beyond this contract's scope; the realistic-volume
  fixture is deliberately sized to prove the existing plain-list approach still reads correctly, not
  to force a redesign.
