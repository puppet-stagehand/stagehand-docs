*CloudFront — the named exception.* Five actions have no IAM resource type at all and therefore
cannot be ARN-scoped: `cloudfront:CreateDistribution`, `cloudfront:CreateCachePolicy`,
`cloudfront:CreateResponseHeadersPolicy`, `cloudfront:CreateOriginAccessControl`, and
`cloudfront:CreateFunction`. Grant exactly those five in a single dedicated statement whose `Sid`
names them as the unscopable set, on an unrestricted resource, with **no condition block**. This is
user decision D-A: grant them unscoped, state the gap plainly in the runbook (plan 01-04), and do not
split the apply role. Do not
attach request-tag or tag-key conditions to them: whether the AWS provider sends tags on the create
call is provider-internal behaviour that the research explicitly did not confirm, and a wrong
condition denies a legitimate apply with an error naming an action the policy visibly grants — the
most expensive possible failure to debug during Phase 2's first real apply. Grant
`cloudfront:TagResource` alongside them, because the tagged-create operation requires both. Every
other CloudFront action — the update, delete, get, describe, publish, and list-tags verbs — goes in
separate statements scoped to `arn:<partition>:cloudfront::<account>:distribution/*`,
`cache-policy/*`, `response-headers-policy/*`, `origin-access-control/*`, and, for the function,
the exact `function/stagehand-${each.key}-site-paths`. Keep the unscopable five isolated in their own
`Sid` so a reviewer can see the residual surface at a glance and so plan 01-04's runbook amendment
has a single place to point at. The compensating controls for this residual are human apply,
CODEOWNERS review on `/infra/`, and a second administrator's review of the trust and permission
policies — all three already exist and all three stay.

*ACM.* `acm:RequestCertificate` also has no resource type, but it does support a domain-names
condition key, which is the strongest lever available anywhere in this policy. Grant it on an
unrestricted resource with a condition block containing BOTH a `Null` guard on the domain-names key
set to `"false"` AND a `ForAllValues:StringEquals` on that key whose value list is
`local.site[each.key].domain_names`. The `Null` guard is mandatory, not stylistic: in an `Effect:
Allow` statement a `ForAllValues` operator evaluates true when the context key is absent, so without
the guard a request carrying no domain names is allowed and the restriction evaporates. Pin the
validation-method key to `DNS` (it is a scalar — never put a set operator on it). Add an
`aws:RequestedRegion` condition pinning ACM to `us-east-1`, since the certificate is created through
the `us_east_1` provider alias. The remaining ACM verbs scope to `certificate/*`.

`arn:<partition>:route53:::hostedzone/${var.hosted_zone_id}` with a record-types condition pinned to

each set-operator condition again paired with its `Null` guard. Build the allowed record-name list

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → AWS STS | The apply Environment's OIDC token is exchanged for the most privileged CI credentials in the account. |
| Apply role → the rest of the AWS account | The apply role holds create and delete authority. Everything outside its ARN and prefix scoping is what an escape would reach. |
| Apply role → IAM | The apply role creates and policies another role, which is an IAM-write authority held by a CI-assumable identity. |
| Merged diff → apply-role permissions | A pull request can propose widening the apply role's own policy. |
