# Phase 04.2: Code Review Report

**Reviewed:** 2026-08-31T11:05:00Z
**Depth:** standard
**Files Reviewed:** 17
**Status:** issues_found

## Summary

Reviewed the Downloads page feature (client-side channel-scoped release rendering, the
`loadDownloads()`/`parseChecksums()` GitHub Releases loader, the `/data/downloads.json`
endpoint, deploy/route/link-check script updates, and three new docs pages). Unit test
coverage of `downloads.ts` is strong and the deploy/route/invalidation-list additions are
internally consistent (verified by rebuilding the site and re-running `check:routes`,
`check:invalidation`, `check:links`, `eslint`, `prettier --check`, `astro check`, and the
relevant `vitest` suites — all pass).

Two real problems were found by tracing execution rather than just reading the diff:

1. `loadDownloads()` documents an explicit "never throw" contract for the whole function, but
   only the initial fetch/parse of the releases list is guarded — a structurally-unexpected
   (but still `200 OK`, still valid-JSON) GitHub API response can throw a `TypeError` that
   escapes `loadDownloads()` uncaught, which at build time means the **entire static site
   build fails**, not just the Downloads page. This is a genuine regression risk against the
   feature's own stated invariant.
2. The new `<noscript>` fallback link on the Downloads page is invisible to the site's own
   external-link governance (`scripts/check-built-links.ts`), because it uses `parse5`'s
   default "scripting enabled" parse mode, under which `<noscript>` content is raw text, not
   DOM. The build passes today by accident, not by design — the URL was never actually
   checked against the allowlist.

Also flagged: unlike the closely-mirrored `TesterGuideVisibility.astro` (which has a
dedicated Playwright spec covering fail-closed and hostname-based reveal behavior),
`DownloadsChannelVisibility.astro`'s actual DOM-wiring script has zero test coverage — only
the pure helper functions it calls are unit-tested.

## Critical Issues

### CR-01: `loadDownloads()` can throw out of its own documented "never throw" contract on a malformed-but-successful GitHub API response

**File:** `src/lib/data/downloads.ts:88-104`

**Issue:** The function's own doc comment (lines 76-83) states: "Any failure — a thrown
error, a non-ok status, or unparseable JSON from the releases-list fetch — resolves every
channel to null rather than throwing out of `loadDownloads`". In practice, only the initial
`fetch(RELEASES_URL)` + `response.json()` call is wrapped in `try`/`catch` (lines 89-95).
The per-release processing that follows is not:

```ts
const result = emptyDownloads();

for (const channel of RELEASE_CHANNELS) {
  const matchedRelease = findLatestForChannel(releases, channel);   // releases.find(...)
  if (!matchedRelease) continue;

  const checksumsAsset = matchedRelease.assets.find((asset) => asset.name === 'SHA256SUMS'); // <- not guarded
  if (!checksumsAsset) continue;

  try {
    ...
  } catch {
    continue;
  }
}
```

`releases` is cast with `as GitHubRelease[]` (line 92) with **zero runtime shape
validation** — unlike `loadCompatibility()` elsewhere in this codebase, which validates its
local YAML against a JSON Schema before use. If the GitHub API ever returns a `200` with a
JSON body that parses but doesn't match the assumed shape (e.g. an object instead of an
array, rate-limit/error payload mixed into a 200, a release entry missing `assets`, or
`assets` being `null`), `releases.find(...)` or `matchedRelease.assets.find(...)` throws a
`TypeError` that is **not** caught anywhere in `loadDownloads`. Because this function is
awaited directly inside two Astro static-route components (`src/pages/downloads/index.astro`
and `src/pages/data/downloads.json.ts`), an uncaught throw here fails the entire `astro
build` — taking down every page on the site, not just Downloads — which directly
contradicts the "must degrade... never throw" contract the file itself documents.

**Fix:** Extend the try/catch to cover the whole per-channel body, and defensively validate
that `releases` is actually an array before use:

```ts
export const loadDownloads = async (
  fetchImpl: typeof fetch = fetch,
): Promise<DownloadsByChannel> => {
  let releases: GitHubRelease[];
  try {
    const response = await fetchImpl(RELEASES_URL);
    if (!response.ok) return emptyDownloads();
    const body = await response.json();
    if (!Array.isArray(body)) return emptyDownloads();
    releases = body as GitHubRelease[];
  } catch {
    return emptyDownloads();
  }

  const result = emptyDownloads();

  for (const channel of RELEASE_CHANNELS) {
    try {
      const matchedRelease = findLatestForChannel(releases, channel);
      if (!matchedRelease) continue;

      const checksumsAsset = matchedRelease.assets?.find((asset) => asset.name === 'SHA256SUMS');
      if (!checksumsAsset) continue;

      const checksumsResponse = await fetchImpl(checksumsAsset.browser_download_url);
      if (!checksumsResponse.ok) continue;
      const checksums = parseChecksums(await checksumsResponse.text());
      if (Object.keys(checksums).length === 0) continue;

      const downloadUrls: Record<string, string> = {};
      for (const asset of matchedRelease.assets) {
        if (asset.name === 'SHA256SUMS') continue;
        downloadUrls[asset.name] = asset.browser_download_url;
      }

      result[channel] = {
        version: matchedRelease.tag_name,
        publishedAt: matchedRelease.published_at,
        checksums,
        downloadUrls,
        htmlUrl: matchedRelease.html_url,
      };
    } catch {
      // Malformed data for one release/channel must never crash the whole build.
      continue;
    }
  }

  return result;
};
```

Add a unit test asserting `loadDownloads` resolves to all-`null` (not throw) when a release
entry is missing `assets` or `releases` isn't an array — the existing test suite only covers
HTTP-level and checksum-parsing failure modes, not malformed-shape JSON.

## Warnings

### WR-01: The Downloads page's `<noscript>` external link is never actually validated by the site's link-check pipeline

**File:** `src/pages/downloads/index.astro:61-69` (link at line 65); root cause in
`scripts/check-built-links.ts:35-50`

**Issue:** This phase adds the site's first (and only) `<noscript>` block:

```astro
<noscript>
  <p>
    JavaScript is required to determine which release channel applies to this site. Browse
    every published release directly on <a
      href="https://github.com/puppet-stagehand/stagehand-release/releases"
      >puppet-stagehand/stagehand-release</a
    >.
  </p>
</noscript>
```

This URL is **not** present in `allowedNonClaimLinks` in `scripts/check-built-links.ts`
(only `.../stagehand-release/issues` and the Bolt help link were added alongside it). By
inspection this looks like it should fail `npm run check:links` (called from `npm run
verify`). It doesn't — verified directly:

```
$ npx tsx scripts/check-built-links.ts   # → 0 external/canonical links visited inside <noscript>
$ node --import tsx scripts/check-links.ts
Verified 6 exact external link targets
Verified 35 canonical first-party link targets locally
```

The reason: `check-built-links.ts`'s `linkAttributes()` walks the tree returned by `parse5`'s
`parse()`, which by default parses in "scripting enabled" mode — under that mode, `<noscript>`
content is treated as a single raw-text node, never expanded into child `<a>` elements
(confirmed by direct `parse5` reproduction: an `<a href>` placed inside `<noscript>` produces
zero visited `attrs` for that anchor). So the new external link ships to production having
**never gone through the site's own external-link allowlist/canonical-link check** — the
build passes by accident, not because the link was vetted. If this URL is ever renamed,
mistyped in a future edit, or 404s, `npm run check:links`/`npm run verify` will not catch it.

**Fix:** Either (preferred, fixes the blind spot generally) make `check-built-links.ts` also
parse `<noscript>` bodies as HTML fragments:

```ts
const visit = (node: DefaultTreeAdapterTypes.Node): void => {
  if ('attrs' in node) {
    for (const attribute of node.attrs) {
      if (attribute.name === 'href' || attribute.name === 'src') values.push(attribute.value);
    }
  }
  if ('tagName' in node && node.tagName === 'noscript' && 'childNodes' in node) {
    const [textNode] = node.childNodes;
    if (textNode && 'value' in textNode) {
      values.push(...linkAttributes(textNode.value)); // re-parse the raw text as a fragment
    }
  }
  if ('childNodes' in node) {
    for (const child of node.childNodes) visit(child);
  }
  if ('content' in node) visit(node.content);
};
```

or, at minimum, explicitly add
`'https://github.com/puppet-stagehand/stagehand-release/releases'` to
`allowedNonClaimLinks` so the intent is documented even though the checker currently can't
see it, and add a regression test fixture under `tests/fixtures/links/` with a `<noscript>`
link to prove the checker actually inspects it (or documents that it deliberately doesn't).

### WR-02: No test exercises `DownloadsChannelVisibility.astro`'s actual DOM behavior, unlike its stated model (`TesterGuideVisibility.astro`)

**File:** `src/components/DownloadsChannelVisibility.astro:8-19`; compare
`tests/e2e/tester-guide-visibility.spec.ts`

**Issue:** The component's own header comment says it "Mirrors `TesterGuideVisibility.astro`'s
external, non-`is:inline` `<script>` pattern, extended to a three-way toggle." That mirrored
component has a dedicated Playwright spec
(`tests/e2e/tester-guide-visibility.spec.ts`) proving, in a real browser, that (a) with JS
disabled the fail-closed fallback is shown, and (b) with JS enabled on specific hostnames the
correct content is revealed and the wrong content stays hidden.

`DownloadsChannelVisibility.astro` has no equivalent. `tests/unit/downloads-channel.test.ts`
only unit-tests `releaseChannelFor()` and `loadDownloads()` (pure functions, no DOM). Nothing
in the current suite would catch, for example, a typo in the `[data-channel="${releaseChannel}"]`
selector, a wrong import path, or the script never running/erroring before
`removeAttribute('hidden')` — all of which would silently leave the Downloads page blank for
every visitor on a production hostname, since `astro build`/`astro check` only type-check and
bundle the script, they don't execute it against `window.location.hostname`.

**Fix:** Add a Playwright spec parallel to `tester-guide-visibility.spec.ts`, using the same
`--host-resolver-rules` technique, asserting that for each of `testpilots.puppet-stagehand.com`,
`beta.puppet-stagehand.com`, and `www.puppet-stagehand.com`, exactly the matching
`[data-channel="..."]` section is visible and the other two stay `hidden`.

## Info

### IN-01: All failure paths in `loadDownloads()` are silently swallowed with no logging

**File:** `src/lib/data/downloads.ts:93-95, 125-127`

**Issue:** Every `catch` block in `downloads.ts` discards the error with no `console.warn`/
`console.error`, by design ("must degrade... never throw"). That's correct for keeping the
build green, but it also means a persistent GitHub API outage, a renamed endpoint, or an
auth/rate-limit change would silently render every channel as "not published yet" with
**zero signal** in CI/build logs — nobody would know until someone manually checks the
Downloads page in production.

**Fix:** Add non-fatal `console.warn` calls in each catch branch (e.g. `console.warn('[downloads]
releases fetch failed:', error)`), which doesn't affect the "never throw" contract but gives
operators a build-log breadcrumb when the feature silently degrades.

### IN-02: `expectedBinaries` is a hand-maintained, untested duplicate of an external naming convention

**File:** `src/pages/downloads/index.astro:13-19`

**Issue:** The five-entry `expectedBinaries` list is annotated as coming from
"puppet-installer/docs/releasing.md's naming pattern" — a convention that lives in a
different repository entirely. There's no shared constant, schema, or test asserting this
list stays in sync with whatever `puppet-installer`'s release workflow actually produces; a
rename on the release side (e.g. `puppet-installer-linux-amd64` → `puppet-installer_linux_amd64`)
would silently degrade every row to "download link unavailable" / "checksum unavailable"
with no build-time signal, similar in spirit to IN-01.

**Fix:** Not urgent given the "never invents a link" design is itself intentional, but
consider a lightweight unit test (using a realistic fixture asset list) asserting all five
expected filenames are matched, so a naming-convention drift is caught by CI instead of
discovered by a tester looking at a page full of "unavailable" rows.
