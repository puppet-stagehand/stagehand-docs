# Phase 04.2: Tester Downloads - Context

**Gathered:** 2026-08-27
**Status:** Ready for research/planning — blocked on cross-repo prerequisite (see below)

<domain>
## Phase Boundary

A reader on any of the three sites (testpilots/beta/stable) can download the puppet-installer
binary matching that site's release channel, sourced from a public GitHub Releases mirror repo,
and reach ported user/installer documentation. The downloads page is NOT gated — only the
Tester's Guide (Phase 04.1) requires the shared password. Requirements: DOWN-01 through DOWN-04,
DOC-02, DOC-03, GATE-07.

This phase does NOT build a private-S3-origin download path or a ghcr container channel — the
original 2026-08-26 design for this phase (see REQUIREMENTS.md's amendment notes) is superseded.

</domain>

<decisions>
## Implementation Decisions

### Source of truth for the binary (the central decision for this phase)
- **D-01:** `puppetlabs-seteam/puppet-installer` is a **private/internal** GitHub repo. Its release
  workflow (`.github/workflows/release.yml`) creates GitHub Releases there on `v*` tags, with
  channel (`stable`/`beta`/`test-pilots`/`development`) derived from which release branch contains
  the tagged commit, stamped into the binary via ldflags and stated in the release body text
  (`Channel: <name>`) — NOT in the tag name itself. A public downloads page cannot link an
  anonymous visitor to a private repo's release assets (401/404 without a token).
- **D-02:** The release workflow already has a "best-effort" mirror step intended to publish the
  same binaries to a public repo — but it targets a placeholder (`souldonetworks/stagehand-release`
  + an unset `STAGEHAND_RELEASE_TOKEN` secret) that doesn't exist. **Corrected target: the public
  repo is `puppet-stagehand/stagehand-release`**, not `souldonetworks/...` — that placeholder name
  in `puppet-installer`'s workflow is wrong and must be fixed as part of the cross-repo
  prerequisite, not carried forward.
  — **Reversibility:** reversible (repo creation, workflow edit, secret rotation are all undoable)
  — **rationale:** creates a durable public artifact source the docs site can read without ever
  handling a credential for the private repo.
- **D-03:** `puppet-stagehand/stagehand-release` also becomes the place testers/customers file
  issues about the **installer or console**. `stagehand-docs` keeps its own repo issues for
  docs-site-specific problems — do not redirect all issue links to the new repo, only
  installer/console ones.
- **D-04:** This phase's own work is entirely inside `stagehand-docs` (the downloads page reading
  the public repo's Releases API). Creating `puppet-stagehand/stagehand-release`, retargeting
  `puppet-installer`'s workflow, and wiring the token are **cross-repo prerequisite work**, tracked
  as a blocker to this phase's DOWN-01/02/04 criteria — not a task this phase's plan performs. See
  the Cross-Repo Prerequisite section in ROADMAP.md's Phase 04.2 entry.

### Per-environment channel resolution (immutable-promotion constraint)
- **D-05:** PROJECT.md locks: "Promotion is ordered and immutable: testpilots → beta → stable, one
  full 40-character SHA" — the exact same built bytes ship to all three environments unchanged.
  Therefore the downloads page CANNOT be built with a different, environment-baked channel per
  site. **Resolution: client-side hostname detection.** The same static HTML/JS ships everywhere;
  a small script reads `window.location.hostname` at runtime and fetches/display the matching
  channel's release data (`testpilots.puppetstagehand.com` → `test-pilots`,
  `beta.puppetstagehand.com` → `beta`, `www.puppetstagehand.com` → `stable`).
  — **Reversibility:** reversible — pure client-side logic, no infra.
  — **Rejected alternative:** an edge/CloudFront-function-based per-distribution rewrite (like the
  AUTH gate's pattern) was considered and explicitly rejected as more infra than needed for a
  page that only needs to change which release it displays, not enforce access control.

### Gating
- **D-06:** The downloads page is explicitly **not** behind the AUTH-01 password gate (this
  reverses the original 2026-08-26 DOWN-03, which assumed one shared gate over both the installer
  and the testing guides). Only the ported Tester's Guide (Phase 04.1, DOC-01/AUTH-06) stays
  gated. Rationale: the page only ever links to public release artifacts on GitHub — there is
  nothing left to protect once the artifact itself is public.

### Zero-releases-today reality
- **D-07:** As of 2026-08-27, `puppetlabs-seteam/puppet-installer` has **zero releases published,
  anywhere** — worse than the original phase's note about `puppet-stagehand/stagehand` having zero
  release *assets* (that repo at least had a tagged release). DOWN-04's honest-unavailable-state
  requirement is not a hypothetical edge case here — it is the default state the page ships in
  until the cross-repo prerequisite work produces a first real release per channel.

### Documentation porting (folded in from the user-guide/tester-guide ask)
- **D-08:** The general **User Guide** ports from `puppet-console`'s `docs/USER-GUIDE.md` into this
  site's `src/content/docs/` — visible on all three environments (unlike the Tester's Guide, which
  is 04.1's concern and testpilots/beta-only).
- **D-09:** Reader-facing `puppet-installer` docs are folded in alongside it:
  `docs/registry-distribution-guide.md` and `docs/support-guide.md`. Maintainer-facing installer
  docs (`docs/releasing.md`, `docs/secrets.md`, `docs/production-readiness.md`) are explicitly
  **excluded** — they document internal release engineering / secrets handling, not customer-
  facing product use.

### Claude's Discretion
- Exact page layout/copy for `/downloads/`, how the checksum/publication-date data is fetched and
  cached (build-time vs runtime GitHub API call), and how the ported docs are organized within
  `src/content/docs/` (flat vs subdirectory) are left to the planner.
- Whether the GitHub Releases API call happens client-side (fetch on page load) or is pre-fetched
  at build time and baked into static JSON (similar to the existing `/data/compatibility.json`
  pattern) is a research question — GATE-07's fixture-based test should work either way, but rate
  limits and staleness tradeoffs should be researched before locking this in.

</decisions>

  codebase, and it's edge-based (CloudFront function), not client-side — deliberately NOT reused
  here per D-05's rejected-alternative note.

<specifics>
## Specific Ideas

- Downloads page shows one binary download (matching the visitor's site/channel), not a matrix of
  all channels — a testpilots visitor sees the test-pilots build front and center, not a picker.
- Checksum and publication date must be visibly stated next to the download link, not buried in a
  linked page.
