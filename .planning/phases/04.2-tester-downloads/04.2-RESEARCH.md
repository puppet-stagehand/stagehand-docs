## Summary

This phase's central research question — client-side fetch vs. build-time fetch for GitHub Releases
data — has a clear, directly-verified answer: **build-time fetch, mirroring the existing
`/data/compatibility.json` pattern.** Two independent findings drive this, both confirmed live
against the real GitHub API this session, not assumed from training data:

1. **Rate limits are shared and low.** `api.github.com`'s unauthenticated primary rate limit is
   60 requests/hour, and — critically — it is bucketed **per source IP, not per site visitor**
   (confirmed via a direct fetch of GitHub's own rate-limit docs: "Unauthenticated requests are
   associated with the originating IP address, not with the user or application that made the
   request"). Any shared corporate NAT, VPN, or mobile carrier IP pool serving multiple testers
   would exhaust this budget quickly on a page that calls the API on every page load.

2. **The checksum data (DOWN-04's hard requirement) is not reachable from the browser at all,
   regardless of rate limits.** A GitHub Release asset's `browser_download_url` (needed to fetch
   and parse `SHA256SUMS`) 302-redirects to `release-assets.githubusercontent.com` /
   Azure Blob Storage, and neither hop sends an `Access-Control-Allow-Origin` header — confirmed
   with a live `curl -I -L` against a real public release asset with an `Origin` header attached.
   `api.github.com` itself *does* send `Access-Control-Allow-Origin: *` (also confirmed live), but
   its JSON response for a release does not carry the per-file checksum — that only exists inside
   the separately-hosted, non-CORS-enabled `SHA256SUMS` text asset. A page that tries to `fetch()`
   and parse that file client-side will get a network-level CORS failure; only a same-origin
   `<a href>` navigation (an actual download) works, not programmatic reading of its contents.

Given both findings, a build-time (Node/CI) fetch — where CORS does not apply — is the only way to
satisfy DOWN-04 at all, and it happens to also be the pattern already established in this codebase
for exactly this shape of problem (`src/lib/data/compatibility.ts` → `src/pages/data/*.json.ts`).
The recommended design: a build-time loader fetches `GET /repos/puppet-stagehand/stagehand-release/releases`,
filters by parsing `Channel: <name>` out of each release's `body` (channel is **not** encoded in the
tag or title — verified by reading `puppet-installer`'s actual release workflow), downloads and
parses the matching release's `SHA256SUMS` asset server-side, and emits one static JSON document
(or a build-time-rendered HTML block per channel) covering all three channels. **Client-side
JavaScript then only does what it already does for the Tester's Guide toggle** — resolve
`window.location.hostname` via the existing, unmodified `resolveSiteChannel()` and show the one
channel block that matches, exactly mirroring `TesterGuideVisibility.astro`. No client-side GitHub
API call, no rate-limit exposure, no CORS problem, and staleness is bounded by this project's normal
build/promote cadence (documented as a known, acceptable limitation — see Pitfall 2).

The cross-repo prerequisite (`puppet-stagehand/stagehand-release` existing, wired, and populated
with at least one release per channel) is **confirmed not yet done**: `gh repo view
puppet-stagehand/stagehand-release` returns "Could not resolve to a Repository" against this
session's authenticated GitHub CLI. This phase's own code can and should still be built and tested
against fixtures (per GATE-07 and D-07), but DOWN-01/02/04 cannot be verified against the real live
repo until that prerequisite lands — this is expected, not a research gap.

Documentation porting (DOC-02/DOC-03) follows Phase 04.1's already-proven curate-don't-verbatim-port
pattern. `USER-GUIDE.md` (991 lines) is mechanically clean (no images, no relative links, no
internal-doc references) but long enough to need the same trimming Phase 04.1 applied to
`TESTER-GUIDE.md` (1375 → 236 lines). `registry-distribution-guide.md` (194 lines) is short and
mostly clean but references two not-yet-merged internal spec documents by path that must not be
carried into the port. `support-guide.md` (507 lines) is the one open question: its own header
frames it as "Internal reference for Support and PS engineers troubleshooting puppet-installer with
customers," and its body is full of Go package paths (`internal/modes/allinone`,
`cmd/puppet-installer`) — this reads as an internal support runbook, not customer-facing product
documentation, despite D-09 characterizing it as reader-facing. Flagged as an Open Question for the
planner/human, following the same pattern Phase 04.1 used for `TESTER-GUIDE.md`'s audience mismatch.

**Primary recommendation:** Build-time-fetched, per-channel static JSON (new
`src/lib/data/downloads.ts` + `src/pages/data/downloads.json.ts`, following
`compatibility.ts`/`compatibility.json.ts` exactly) feeding a `/downloads/` page that pre-renders
all three channels' blocks and uses a `DownloadsChannelVisibility.astro`-style companion script
(mirroring `TesterGuideVisibility.astro`) to show only the visitor's channel at runtime. Curate
(don't verbatim-port) `USER-GUIDE.md`; escalate `support-guide.md`'s audience fit as an open
question before committing to full inclusion.

### Pattern 1: Build-time fetch, runtime hostname-based reveal (the phase's core pattern)
**What:** All network/API work happens once, at build time, server-side (Node), where CORS and
per-visitor rate limits do not apply. The browser only ever does local DOM work against data
already embedded in the static HTML/JSON.
**When to use:** Any per-environment content variation under this project's immutable-promotion
constraint (PROJECT.md) — this is the second application of the pattern Phase 04.1 established
for the Tester's Guide; treat it as the project's standard answer to "this looks different on
different hosts but there's only one build."
**Example — build-time loader, mirroring `compatibility.ts`'s shape:**
```typescript
// Source: this repository, src/lib/data/compatibility.ts (existing pattern, read this session)
// New file: src/lib/data/downloads.ts (recommended shape)
export interface ChannelRelease {
  version: string;
  publishedAt: string; // ISO date, from the GitHub release's `published_at`
  checksums: Record<string, string>; // filename -> sha256, parsed from SHA256SUMS
  htmlUrl: string; // link to the GitHub Release page itself
}

export type DownloadsByChannel = Record<'test-pilots' | 'beta' | 'stable', ChannelRelease | null>;

export const loadDownloads = async (
  fetchImpl: typeof fetch = fetch, // injectable — see GATE-07 pattern below
): Promise<DownloadsByChannel> => {
  // 1. GET /repos/puppet-stagehand/stagehand-release/releases
  // 2. filter by parsing "Channel: <name>" out of release.body (verified format —
  //    see puppet-installer/.github/workflows/release.yml's `notes:`/`body:` steps)
  // 3. for the newest match per channel, GET its SHA256SUMS asset and parse
  // 4. channel absent from the release list -> null, NOT a thrown error and NOT omitted
  //    (DOWN-04 requires an explicit unavailable state per channel, not a missing key)
};
```

### Pattern 3: Injectable fetch for fixture-based testing (the GATE-07 pattern)
**What:** Any function that performs a network call takes an optional `fetchImpl` parameter
defaulting to the real `fetch`, so tests can substitute a `vi.fn()` stub returning canned
responses — no real network access needed in CI, no `nock`/`msw` dependency needed either.
**When to use:** `loadDownloads()` above, and any GATE-07 test exercising channel resolution
against fixture release data.
**Example (the exact existing precedent):**
```typescript
// Source: this repository, scripts/check-live-deployment.ts + tests/unit/check-live-deployment.test.ts
// (read this session, verbatim below)

// In the implementation:
export type FetchLike = (url: string, init?: RequestInit) => Promise<Response>;
export const verifyLiveDeployment = async ({
  fetchImpl = (url, init) => fetch(url, init),
  // ...
}: { fetchImpl?: FetchLike /* ... */ }) => {
  /* ... */
};

// In the test:
const buildFetchStub = (overrides: Record<string, StubResponse | StubResponse[]>) => {
  const responses = { ...passingResponses(), ...overrides };
  const callCounts = new Map<string, number>();
  return vi.fn(async (input: string | URL, _init?: RequestInit) => {
    const path = new URL(String(input)).pathname;
    const attempt = callCounts.get(path) ?? 0;
    callCounts.set(path, attempt + 1);
    const entry = responses[path];
    const resolved = Array.isArray(entry)
      ? (entry[Math.min(attempt, entry.length - 1)] ?? entry.at(-1))
      : entry;
    return new Response(resolved?.body ?? '', { status: resolved?.status ?? 200 });
  });
};
```
For GATE-07, the equivalent fixtures should cover (per the CONTEXT.md research question): a
release existing for a channel, a channel with **no** matching release (must resolve to the
unavailable state, not fall through to another channel's data or a stale cached value — this is
GATE-07's literal wording), and a release with/without a parseable `SHA256SUMS` asset.

### Pattern 4: Client-side channel-scoped visibility toggle (reuse, don't reinvent)
**What:** A component-scoped `<script>` that reads `resolveSiteChannel(window.location.hostname)`
and toggles `hidden` attributes on pre-rendered DOM blocks.
**When to use:** Exactly this phase's need — toggling among the three pre-rendered channel blocks.
**Example (the exact existing precedent, read this session, verbatim):**
```astro
---
// Source: this repository, src/components/TesterGuideVisibility.astro
---
<script>
  import { resolveSiteChannel } from '../lib/site-channel';

  const guide = document.querySelector<HTMLElement>('[data-tester-guide]');
  const fallback = document.querySelector<HTMLElement>('[data-tester-guide-unavailable]');
  const channel = resolveSiteChannel(window.location.hostname);
  const allowed = channel === 'testpilots' || channel === 'beta';

  if (!allowed) {
    guide?.setAttribute('hidden', '');
    fallback?.removeAttribute('hidden');
  }
</script>
```

## Common Pitfalls

### Pitfall 1: Client-side `fetch()` of a release asset is CORS-blocked, not just rate-limited
**What goes wrong:** A plan that tries to `fetch()` the `SHA256SUMS` asset (or any binary) directly
from browser JavaScript to read/display its contents will fail silently or with a console-only CORS
error — the network request may even succeed at the HTTP level (redirect chain returns 200), but the
browser refuses to let JavaScript read the response body because no `Access-Control-Allow-Origin`
header is present on either the `github.com` redirect or the final
`release-assets.githubusercontent.com`/Azure Blob response.
**Why it happens:** GitHub Release *asset downloads* are served through a different code path
(redirecting to blob storage) than the `api.github.com` REST JSON responses, which do set
`Access-Control-Allow-Origin: *`. Confidence that this JSON endpoint is CORS-open does not transfer
to the asset-download path.
**How to avoid:** Fetch and parse `SHA256SUMS` at build time (Node, no CORS), embed the parsed
checksum values into the static JSON/HTML. The actual *download* of the binary itself is a normal
`<a href>` navigation (not a `fetch()`), so that part is unaffected by CORS regardless.
**Warning signs:** A plan or task that describes "the page fetches the checksum file and displays
the matching line" without specifying *where* that fetch runs (build vs. browser) — verify it's the
build tier before accepting the task as written.
**Verified this session:** `curl -sI -L "$ASSET_URL" -H "Origin: https://example.com"` against a
real public GitHub release asset returned zero `access-control-*` response headers anywhere in the
redirect chain.

### Pitfall 2: Build-time data goes stale across the immutable promotion pipeline
**What goes wrong:** Because the SAME static build promotes testpilots → beta → stable (PROJECT.md,
verbatim: "Promotion is ordered and immutable: testpilots → beta → stable, one full 40-character
SHA" [VERIFIED: .planning/PROJECT.md:165]) over what this project's own release history shows can be
a multi-day window (see Phase 5's actual wave-by-wave promotion in ROADMAP.md), a release cut after
the build but before an environment's promotion will not be reflected on that environment until the
next full rebuild-and-repromote cycle.
**Why it happens:** This is an inherent tradeoff of the build-time-fetch recommendation, not a bug
— it trades live-updating data for CORS/rate-limit safety and architectural consistency with
`compatibility.json`'s own already-accepted staleness model (that data has an explicit
`last_verified`/365-day freshness contract precisely because it's build-time-computed, not live).
**How to avoid:** Do not treat this as something to engineer around (e.g., do not add a client-side
"check for newer release" call — that reintroduces Pitfall 1's constraints). Instead, document it:
state the publication date on the page (already required by DOWN-04) so a reader can judge
freshness themselves, and note in an operations doc that a new release requires a rebuild+redeploy
to appear on the downloads page, the same operational reality every other build-time-computed page
on this site already has.
**Warning signs:** A task or plan implying the downloads page will "always show the latest release
in real time" — that promise cannot be kept under the immutable-promotion constraint without
reintroducing the CORS/rate-limit problems this research rules out.

### Pitfall 3: `SiteChannel`'s `'testpilots'` string is NOT the release's `'test-pilots'` string
**What goes wrong:** A direct string comparison between `resolveSiteChannel()`'s output and the
release-channel value parsed from a GitHub release body will never match for the testpilots case,
silently falling through to the unavailable state on the one environment where a release DOES
exist.
**Why it happens:** Two independently-named enumerations exist in this codebase and its upstream
data source, and they use different spellings for the same concept:
- `SiteChannel` (`src/lib/site-channel.ts`, read this session): `'testpilots' | 'beta' | 'stable' | 'unknown'`
  — verbatim: `export type SiteChannel = 'testpilots' | 'beta' | 'stable' | 'unknown';`
  [VERIFIED: src/lib/site-channel.ts:12]
- The release channel stamped by `puppet-installer`'s workflow (read this session): `stable` /
  `beta` / **`test-pilots`** (with a hyphen) / `development` — verbatim from the channel-detection
  step: `elif echo "$contains" | grep -q 'origin/main';   then CH=test-pilots`
  [VERIFIED: puppet-installer's release.yml determine-channel step, read this session]
**How to avoid:** The downloads page's data-loading/rendering code must explicitly map
`resolveSiteChannel()`'s `'testpilots'` to the release data keyed `'test-pilots'` (and `'beta'` to
`'beta'`, `'stable'` to `'stable'`, which do match). Do not assume the two vocabularies are
interchangeable anywhere a comparison or object-key lookup happens.
**Warning signs:** A `downloads.json` schema or lookup object keyed with `'testpilots'` (no hyphen)
instead of `'test-pilots'` — this would silently never match a real release once the cross-repo
prerequisite lands, and unit tests using only `SiteChannel`-shaped fixture keys would not catch it.

## Code Examples

### Fetching and filtering GitHub Releases by channel (build-time, Node)
```typescript
// Illustrative — combines the verified release-body channel format
// (puppet-installer/.github/workflows/release.yml, read this session:
//   body: |
//     Single-binary Puppet Core installer with the console embedded.
//     Channel: `${{ needs.determine-channel.outputs.channel }}`
// ) with the verified GitHub REST API shape (api.github.com, queried live this session).
const RELEASE_CHANNEL_PATTERN = /^Channel:\s*`?([\w-]+)`?/m;

interface GitHubRelease {
  tag_name: string;
  body: string | null;
  published_at: string;
  assets: { name: string; browser_download_url: string }[];
}

function findLatestForChannel(
  releases: GitHubRelease[],
  channel: 'test-pilots' | 'beta' | 'stable',
): GitHubRelease | undefined {
  // releases[] arrives newest-first (GitHub's documented default sort by created_at —
  // confirmed via docs.github.com/en/rest/releases/releases, fetched this session:
  // "sorted by the created_at attribute"), so the first match IS the latest for that channel.
  return releases.find((release) => {
    const match = RELEASE_CHANNEL_PATTERN.exec(release.body ?? '');
    return match?.[1] === channel;
  });
}
```

### Parsing `SHA256SUMS` (build-time, once the matching release/asset is found)
```typescript
// The file's own format, per puppet-installer/.github/workflows/release.yml
// (`sha256sum puppet-installer-* > SHA256SUMS`) is the standard `sha256sum` output:
// "<hex-digest>  <filename>\n" per line.
function parseChecksums(sha256sumsText: string): Record<string, string> {
  const checksums: Record<string, string> = {};
  for (const line of sha256sumsText.trim().split('\n')) {
    const [digest, filename] = line.trim().split(/\s+/);
    if (digest && filename) checksums[filename] = digest;
  }
  return checksums;
}
```

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-------------------|
| V2 Authentication | No | Downloads page is explicitly ungated (D-06/DOWN-03) — no auth surface added |
| V3 Session Management | No | No session state introduced |
| V4 Access Control | Yes (negative control) | The one access-control obligation is that `/downloads` must **stay** unlisted in `gated-paths.json` — verified current state: `["/docs/testers-guide"]` only |
| V5 Input Validation | Yes | Parsed `SHA256SUMS`/release-body text is untrusted external input (from a public GitHub repo, potentially mirror-step-controlled by anyone with write access to `puppet-stagehand/stagehand-release`) — the build-time parser (Code Examples above) must handle malformed lines/missing fields without crashing the build (return `undefined`/skip, don't throw), same defensive posture as `loadYaml`'s schema validation for `compatibility.yaml` |
| V6 Cryptography | No hand-rolled crypto | The SHA256 digest is consumed as pre-computed text, never recomputed or verified server-side in this phase — if a future phase adds "verify the downloaded file's hash automatically," use the Web Crypto API's built-in `SubtleCrypto.digest`, never a custom/hand-rolled hash implementation or a third-party JS SHA256 library |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| A malformed or adversarial `SHA256SUMS`/release body (from a compromised or misused mirror-repo write access) crashing the site build | Tampering | Defensive parsing (regex `.exec()` returning `undefined` on no match, `.find()` returning `undefined` when no channel matches) rather than assuming well-formed input — never let a build-time fetch/parse failure take down the whole site build; degrade to the honest-unavailable state for that one channel instead |
| Displaying a stale or wrong checksum that a reader trusts blindly | Tampering / Repudiation | State the publication date alongside the checksum (already required by DOWN-04) so staleness is visible, not hidden; never synthesize/guess a checksum value if the `SHA256SUMS` asset is missing or unparseable — fall back to the unavailable state for that channel instead |
| Leaking any credential for the private `puppetlabs-seteam/puppet-installer` repo into this public repo or its shipped browser bundle | Information Disclosure | This phase's own scope never touches that repo or its token at all (D-02/D-04) — the build-time fetch target is exclusively the already-public `puppet-stagehand/stagehand-release` repo's public API, which needs no authentication |
