## ADR-0001: Ship an empty, evidence-bearing compatibility registry
- source: docs/adr/0001-compatibility-scaffold.md
- status: locked (Accepted, 2026-08-26)
- decision: (1) The published compatibility registry ships empty — `src/data/compatibility.yaml` holds `schema_version: 1` and `records: []` until a claim completes Stagehand release verification; no record is published to satisfy a completeness or presentation goal. (2) Representative compatibility data lives only in test fixtures — `tests/fixtures/data/compatibility-e2e.yaml` carries five records spanning every `status` value and every tier, loaded only when `STAGEHAND_E2E_FIXTURES=1`; fixture records are not compatibility claims and must never be promoted into `src/data/compatibility.yaml`. (3) Every published record carries primary evidence and a truthful verification date — the schema makes `evidence_url` and `last_verified` required; `loadCompatibility` rejects a non-HTTPS evidence URL, a future `last_verified`, and evidence older than 365 days; validation is never weakened to admit a record that cannot meet the evidence policy. (4) The empty state is a supported rendering, not a placeholder — `src/components/CompatibilityEmptyState.astro` tells the reader that no claim has completed verification and that untested combinations must be treated as unverified.
- amendment: The design specification's delivery boundary is amended so that "representative compatibility data" means representative fixture data exercised by the test suite, together with a rendered empty state on the published site. It does not mean seeded customer-facing records.
- scope: compatibility registry, src/data/compatibility.yaml, test fixtures, compatibility claims policy, empty state rendering, schema validation, build-time isolation check
- enforced by: scripts/check-e2e-build-isolation.ts (fails the build unless production compatibility output has exactly zero records and end-to-end output has exactly five)
- alternatives rejected: seed the published registry with real fully evidenced records; relax the schema so records may omit evidence until verified; publish the fixture records to the live site

## ADR-0002: Six GitHub Environments, three OpenTofu environments
- source: docs/adr/0002-github-environment-model.md
- status: locked (Accepted, 2026-08-26)
- decision: (1) The three namespaces are named distinctly in all normative text — "OpenTofu environment", "GitHub apply Environment", and "GitHub plan Environment"; the bare word "environment", unqualified, carries no normative force. (2) The three-value enum binds `var.environment` only — `testpilots`, `beta`, and `stable` are the complete set of OpenTofu environments and the complete set of `environment` tag values. (3) Six GitHub Environments exist — three apply Environments named `testpilots`, `beta`, and `stable`, restricted to `main`, carrying the apply and deploy role ARNs, with required reviewers on `beta` and `stable` and self-review prevented on `stable`; three plan Environments named `testpilots-plan`, `beta-plan`, and `stable-plan`, restricted to the custom branch rule `refs/pull/*/merge`, carrying only the plan role ARN, each requiring a trusted reviewer with self-review prevented; plan Environments never hold an apply or deploy role ARN. (4) Planning authority and apply authority remain separated — no pull-request-triggered workflow may reach a role that can mutate infrastructure or site content; `pull_request_target` is not an acceptable way to make planning easier; the job-level same-repository guard in `infrastructure.yml` runs before a plan Environment is attached and remains required.
- amendment: The implementation plan's global constraint is amended to read: OpenTofu environment names are exactly `testpilots`, `beta`, and `stable`.
- scope: GitHub Environments, OpenTofu environments, var.environment, infrastructure.yml workflow, deploy.yml workflow, AWS IAM role ARNs, pull-request infrastructure planning, environment resource tag
- deferred: Ownership of `AWS_INFRASTRUCTURE_PLAN_ROLE_ARN` and `AWS_INFRASTRUCTURE_APPLY_ROLE_ARN` is explicitly not settled by this ADR (settled subsequently by ADR-0003)
- alternatives rejected: collapse to three GitHub Environments matching the OpenTofu enum; use `pull_request_target` so plan jobs can run against a `main`-only Environment; drop pull-request infrastructure planning entirely

## ADR-0003: The bootstrap root owns the infrastructure plan and apply roles
- source: docs/adr/0003-infrastructure-iam-role-ownership.md
- status: locked (Accepted, 2026-08-26)
- decision: (1) `infra/bootstrap/` creates both roles — the plan role and the apply role become OpenTofu resources in the bootstrap root alongside the shared OIDC provider, and their ARNs become bootstrap outputs in the manner of `github_oidc_provider_arn` and `state_bucket_names`. (2) One role per Stagehand environment per tier; no sharing — six roles in total, each trusting the repository `puppet-stagehand/stagehand-docs` and exactly one GitHub Environment subject with `aud` equal to `sts.amazonaws.com`; plan roles trust the `-plan` Environment subjects, apply roles trust the unsuffixed Environment subjects; a wildcard Environment name in a trust policy is never permitted. (3) The permission scoping in `docs/operations/github-environments.md` is the specification the OpenTofu must satisfy — plan role gets state read, state-lock acquire and release, refresh, and `Get`/`List`/`Describe` only, scoped to its own state bucket and key; apply role gets that plus the minimum create, update, tag, and delete actions the static-site module requires, scoped by known ARNs, hosted zone, name prefixes, and the mandatory `project = "stagehand"` and matching `environment` tag conditions where AWS supports them; where the OpenTofu and the runbook disagree, one is corrected — they are not allowed to drift apart. (4) Bootstrap remains human-applied — no CI job may assume a role able to modify the bootstrap root, and no workflow gains permission to apply it; the two-administrator review requirement is satisfied by `CODEOWNERS` review on `/infra/` plus the administrator performing the apply, and both remain required. (5) Implementation is a separate task — this ADR records ownership; until the OpenTofu exists, the manual provisioning path in `docs/operations/github-environments.md` remains the operative instruction and must not be deleted.
- scope: infra/bootstrap, AWS_INFRASTRUCTURE_PLAN_ROLE_ARN, AWS_INFRASTRUCTURE_APPLY_ROLE_ARN, IAM roles, GitHub OIDC trust policies, GitHub Environments, OpenTofu, static-site module, CODEOWNERS
- depends on: ADR-0002 (the six GitHub Environments these roles bind to)
- open implementation task: the six OpenTofu role resources do not yet exist in `infra/bootstrap/`; ADR-0003 rule 5 defers implementation and preserves the manual provisioning path in the interim
- alternatives rejected: keep both roles as documented manual prerequisites; create the plan role in OpenTofu and leave the apply role manual; create the roles in the environment site stack
